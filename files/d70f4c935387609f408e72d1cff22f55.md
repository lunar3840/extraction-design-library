# 에델 이동·전투 성능 1차 최적화

사용자 지시일: 2026-10-26 KST. 원문 “해봐”는 앞선 성능 분석과 “일반 이동·전투 중”이라는 상황 확인에 대한 구현 승인이다. USER_REQUEST.md 및 ../edel-performance-audit/USER_REQUEST.md와 연결한다. 같은 캐릭터 런타임 개선의 후속이므로 기존 주제 ID에 회차03으로 잇는다. 이전 헤어·파지 전체 검증의 미완료 항목을 이번 완료로 승격하지 않는다.

## 결과와 한계

채택한 CurrentSourceClearanceFieldBudget 좌표 캐시는 동일 입력 Editor 재생에서 헤어 전체 CPU 평균58.6825→56.8811ms(3.06975%)로 감소했다. 실제 소스 포즈80개의 반복 재생에서 기록한 메시·계층 포즈·주요 witness 정보와 작업량이 일치했다. 새 연막 설정에서 Play 진입·360프레임 이동/사격·종료/원래 씬 복원까지 해당 속도 오류의 신규 발생0건을 확인했다.

렉 완전 해소나 게임 전체 FPS 상승을 입증한 결과는 아니다. 헤어 CPU는 여전히 약57ms로 크며 앞선 분석의2ms 목표는 미달이다. 배포 빌드·GPU/Render thread·장시간 전투 성능은 미측정이다. 큰 폭의 개선에는 잔여 정밀 접촉/충돌 계산의 추가 설계가 필요하다.

## 의도와 변경 전

외형·UV·머리색·접촉 허용치·검사 횟수를 유지하면서 반복 계산만 줄인다. GPT-6 Sol high 제작자와 독립 검토자가 별도 staging 범위를 맡고 메인이 Unity 실행·측정·통합을 맡았다. 캐릭터/UI 담당의 명시 반환 후 공유 Unity를 사용했다.

before_editor.png는 수정 전 실제 Editor 화면이다. backup/에 원본 소스와 연막 수정 전 Resources prefab을 보존했다. before_results.json은 실제 A맵3회 이동·조준·사격 기준값, before_frozen.png와 frozen_input.json은 같은 소스 포즈 비교 기준이다. 사후 이미지를 before로 사용하지 않았다. failed-before-01/와 baseline-probe-v2/는 도구 오류/이전 도구 버전 실행으로 분리했고 최종 기준에서 제외했다.

기존에는 bind 로컬 정점·본 로컬 bounds를 같은 shapeEpoch에서도 반복 계산했다. 연막22개에는 x=TwoCurves, y/z=TwoConstants 혼합 모드가 있었고 초기화·복원 때 오류 로그가 다량 발생했다. 수정 전후 live 각80프레임 구간은 모두 신규 오류0이므로 이 오류를 지속 프레임 렉의 단일 원인으로 지정하지 않는다.

## 실제 변경과 채택 판단

- CurrentSourceClearanceFieldBudget.cs: 스킨 파트별 bind 로컬 정점과 본 로컬 bounds를 같은 shapeEpoch 동안 재사용한다. 기존 행렬/가중치 계산 순서를 유지한다. Editor 전용 원본식 대조 스위치·카운터를 제공하되 정상 대조는 꺼져 있다. 추가 캐시 payload는 스킨 파트 정점수 합×약48바이트이며 객체 오버헤드는 별도다.
- StageASmokeV38.cs: Play 초기화 때 Signals의 알려진 legacy 혼합 모드만 같은 범위의 평평한 TwoCurves로 정규화한다. 정상 새 prefab fallback0이며 프레임별 처리는 추가하지 않았다.
- StageASmokeV38Setup.cs: 향후 생성하는 y/z도 같은 FlatRange 함수를 사용한다.
- StageA_Relay_Blockout_v08.prefab: 연막22개 y/z 속도 모드와 곡선 값만 저장 수정했다. 독립 검토에서2,924,729행 중264행만 달라졌고 그 외 모든 줄은 byte 동일했다. 씬 파일은 수정하지 않았다.

처음 시험한 SdHairCollisionMotion 점수/face 스키닝 캐시는 같은 입력에서 별도 효과가 뚜렷하지 않아 완전히 되돌렸다. 최종 Hair SHA는 원본과 같다. after/after2/verify 및 paired-v1-v2/는 폐기 후보 기록이며 최종 결과와 혼합하지 않는다. BodySurfaceProjector·HeadSourceClearanceFieldBudget·SdWeaponPose·EdelIndexSkinBinding·모델·UV·텍스처·맵 배치·충돌·진입/탈출·조명·카메라는 변경하지 않았다.

## 실제 검증

최종 동일 입력은 paired_results.json / MATCHED_SUMMARY.json이다. 실제 이동/조준 소스 포즈80개를 기록하고 같은 Play 세션에서 원본→개선→개선→원본→원본→개선 각80step을 재생했다. 각 회차 첫10step 제외, 모드별210개 CPU 표본이다. 전체 hair.Step 외부 타이머는 CurrentSource BeginFrame을 포함하고 포즈 적용·해시·Bind를 제외한다. oracle 회차는 성능 통계에서 제외한다.

| 헤어 전체 CPU 평균 | 58.6825ms | 56.8811ms |
| 헤어 전체 CPU p95 | 63.2468ms | 61.7759ms |

80포즈×6비교(480쌍)의 digest/작업 카운터 불일치0이다. digest는 전체 스킨 정점·계층 TRS/morph·witness ID/proxy/bary/mobility·주요 카운터/잔차/budget invalid 수를 포함하며, 모든 개별 witness depth/valid/budget bound까지 빠짐없이 해시한 것은 아니다. 원본식 oracle2,189,025회 대조 불일치0이다. 동결20step도 최종 fixed와 기준이 정확히 일치했다.

최종 Current-only에서 Liv/Yui 각각6대표 포즈의 원본/개선/oracle 회귀는 digest·작업량·원본식 불일치0이다. Serin은 이전 V1+V2 조합의6포즈 회귀만 했으며 원본식289,700회 불일치0이다. Serin의 최종 조합 전체 검증으로 표시하지 않는다. 다른 캐릭터6포즈를 성능 벤치마크로 일반화하지 않는다.

일반 A맵은 AI·날씨·조명을 켜고 public Simulate/FireDirection/Reload를 사용했다. 120프레임×3회(40warm+80측정), 사격12회·재장전3회·조준180표본을 확인했다. 사용자 저장은 별도 임시 StageScenePreview 경로로 격리했다. 평균 frame은 before77.7206ms→fixed73.7516ms이나 두 Play의 AI·날씨·시간·작업량이 같지 않아 인과적 FPS 개선률로 보고하지 않는다. 내부 Step은44.0133→44.0727ms로 비슷하며 이 내부 타이머는 캐시 개선 구간인 CurrentSource BeginFrame 갱신을 제외한다. Profiler Main/GC는 유효, Render 카운터는 무효였다.

독립 검토자는 원자료7×80행·480쌍·oracle·코드/asset 해시·최종 연막 결과를 직접 재검사했다. staging/review/FINAL_REVIEW.md를 메인이 읽고 최종 범위와 제한을 반영했다. 넓은 화면만으로 얼굴/검지의 근접 품질 전체를 보증하지 않는다.

## 정리와 라이브러리

최종 소스 해시와 정리 확인은 FINAL_VALIDATION.json, 최종 refresh는 FINAL_REFRESH.txt다. 임시 Editor helper를 VALIDATION_TOOL.cs.txt로 보관하고 Assets에서 제거했다. 기존 refresh helper가 덮어쓴 과거 COMMAND_refresh.txt는 앞선 진단에 보관된 원본으로 복원하고 동일 해시를 확인했다. 각 *_returned.txt와 FINAL_REFRESH.txt는 playing=False·원래 A씬·dirty=False를 확인한다. 캐릭터/UI 담당에게 변경 범위와 명시 반환을 알린다.

LIBRARY_EVIDENCE.json은 원문·결과·요약·검토·전후 이미지만 선택한다.87MB prefab 백업/staging asset·전체 Editor 로그·불필요한 원시 trace는 공개 수집에서 제외하고 로컬 보존한다. 분석 회차02 다음 구현 회차03이며 새 대표 주제를 만들지 않는다.

초기 게시 보류 당시 기록(아래 인증 복구로 해소): 현 실행에 유효한 업로드 인증이 없어 공개 사이트의 회차·원문·이미지 확인을 완료하지 못했다. 기존 라이브러리 담당에게 인계하고 추가 인증 복구/키 교체는 수행하지 않는다. ready와 로컬 저장은 공개 게시 성공을 뜻하지 않는다. 실제 상태는 PUBLICATION_VERIFICATION.json 및 outputs/library-content/current/PUBLISH_LEDGER.json을 기준으로 한다.
