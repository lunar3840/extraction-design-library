# 건물 가림 GPU mask 추가 독립 검토

검토일:2026-10-29. 수정 권한 없이 `visibility/PATCH_MANIFEST.json`의 staging4개와 실제 적용4개를 읽었다. 검토 시점4개 모두 staging/production SHA가 일치했다. 이 담당은 파일·Unity 실행·전역 outline·시야·캐릭터 shader를 변경하지 않았다.

## 최초 prototype01 판정

**첫 GPU prototype은 수용 실패다.** 메인의 `after/after_W03_outside.png`를 직접 열어 선택된 건물 전체가 균일한 cyan으로 바뀌고 플레이어가 cyan ghost처럼 보이는 것을 확인했다. 원래 모델 색을 유지하는 국소 가림 해소 의도를 충족하지 않는다. `main/after_EVIDENCE.txt:4`는 이때 maskReady=true/draws36/surfaces2를 기록한다. Shader 지원·컴파일 성공과 실제 정상 렌더를 구별해야 한다.

`after_W03_inside.png`도 직접 열었다. surfaces0인 내부 시점에서는 원래 벽돌·가구·플레이어 색이 보인다. 따라서 저장된 모든 원본 재질 자체가 cyan으로 덮였다고 단정할 근거는 없다. 활성 reveal/mask 경로에서 실패하는 것으로 범위를 좁힌다.

## 우선 질문: RT/2D flip이 과도하게 위험한가

현재 코드만으로 **이중 flip 결함을 확정할 수 없다.** `StageABuildingV33Reveal.cs:845`는 private RT용 `GL.GetGPUProjectionMatrix(camera.projectionMatrix,true)`를 사용하고, mask와 reveal 양쪽이 같은 VP를 사용한다. `BuildingV33LocalReveal.shader:136~141`는 graphics API가 위쪽 UV 원점을 사용할 때만 Y를 뒤집는다. 동일 RT의 실제 raster 방향과 sample 좌표를 맞추는 조합으로 볼 수 있다.

상하 반전·화면 resize·카메라 이동에서 mask가 실제 머리/발과 정렬되는지는 GPU 픽셀 비교가 필요하다. 하지만 **UV 반전만으로 건물의 aperture 바깥까지 균일 cyan이 되는 현상을 설명하는 것은 약하다.** flip부터 무조건 반대로 바꾸는 수정은 권하지 않는다.

## 렌더 상태·패스: 확정 사항과 가설

1. `StageABuildingV33Reveal.cs:856~878`는 beginCameraRendering에서 private RT와 viewport를 설정하고 draw 후 CommandBuffer를 pool에 반환한다. 명시적인 원래 target/viewport 복구는 없다. 이 사실은 확정이다.
2. 다만 현재 local URP의 `UniversalRenderPipeline.cs:1029` CameraRenderingScope는 CreateCameraData/renderer setup 전에 BeginCameraRendering을 호출한다. 이후 ScriptableRenderer의 per-camera setup과 각 pass target bind가 존재한다. 따라서 복구 없음만으로 현재 GPU 색 오염의 원인이라고 확정하지 않는다. 예외·추가 카메라·RenderGraph 상태 상호작용은 분리 실험 대상이다.
3. 실제 `Assets/Settings/PC_Renderer.asset:69`의 mode2는 local URP enum상 **ForwardPlus**다. Deferred는1이다. 현재 실패를 deferred fallback이라는 전제로 분석하지 않는다.
4. 기존 ToonOutline은 depth/normal 입력을 요청하고 어두운 선 색을 사용한다. 이를 바꾸거나 끄는 것을 해결책으로 삼지 않는다. LocalReveal Forward/DepthNormals 패스 또는 material binding과 callback state가 섞이는지 확인한다.
5. 옛 West cyan cue의 `Refresh()` 코드는 남아 있지만 실제 Resources 맵의 해당 script guid `352456b16356dc8408f68b8604cd497b` component는 `m_Enabled:0`이다(prefab:1978567). 기존 Integration도 west/hall cue를 비활성 저장한다. 현 증거로 옛 cyan overlay가 켜진 것을 원인으로 올리지 않는다.

소유 agent에게 권한 내 최소 분리 실험을 전달했다. 같은 W03 시점에서 다음 두 축을 나누면 된다.

- mask callback을 멈추고 LocalReveal clone을 유지하되 MaskValid0: 계속 cyan이면 mask UV 모양 문제와 구분할 수 있다.
- mask callback은 유지하고 건물 원본 재질을 runtime 메모리에서 복구: 원본도 cyan이면 callback state 쪽, 원본은 정상이고 clone만 cyan이면 LocalReveal pass/material binding 쪽으로 좁힐 수 있다.

추가로 BaseColor/BaseMap/RevealMode/FindPass(ForwardLit·DepthNormalsOnly)와 원본/clone 값을 덤프하고, 필요하면 소유 agent의 전용 diagnostic에서 pass별 상수색을 사용해 실제 camera color에 어떤 pass가 쓰이는지 확인한다. 이 문서는 원인 확정이나 전역 renderer feature 변경 승인이 아니다.

## 깊이·alpha·혼합 재질

- ActorMask는 actor만 별도 depth RT에 그리고 RG에 eye depth/coverage를 쓴다. Reveal은 building surface가 actor depth보다 카메라에 가까울 때만 반응한다. `mask.r/max(mask.g,epsilon)`은 bilinear fringe에서 투명 배경과 섞인 depth의 축소를 보정하는 구조다. 깊이 비교는 정적 의도와 맞지만, 실제 mask가 현 포즈/UV로 그려졌는지는 별도 확인이 필요하다.
- 건물 `IsEligibleMaterial(:564~573)`는 원래 transparent/alpha-cutout slot을 제외하고, 혼합 mesh에서는 해당 원본 slot을 opaque 배열에 그대로 남긴다. veil 쪽은 Mode2로 discard한다. 무조건 모든 유리를 불투명 처리하는 코드는 아니다. 이름이 Glass여도 실제 opaque 재질이면 선택될 수 있다는 현 계획과 구분한다.
- ActorMask의 alpha는 `_ALPHATEST_ON` 또는 `_AlphaClip`인 원본에서 BaseMap alpha×BaseColor alpha와 cutoff로만 재현된다. **일반 alpha-blended actor material은 full polygon coverage가 된다.** 코드를 통해 확인되는 지원 한계이며, 현재 캐릭터의 해당 슬롯 사용 여부·실제 아티팩트는 아직 확정하지 않았다. 머리카락/장비의 blended slot이나 별도 shader vertex deformation이 있는지 실제 장착 상태를 확인해야 한다.
- Source BaseMap ST와 Cull은 복사한다. 현재 CharacterHybridD15의 기본 UV0·BaseMap/AlphaClip 경로와 정적으로 맞는다. CommandBuffer.DrawRenderer가 현재 skinned renderer를 사용하므로 별도 정적 mesh 복제는 하지 않지만, callback이 카메라 culling 이전이라는 점에서 첫 프레임/보행/머리카락/블렌드셰이프의 실제 GPU 포즈 정렬은 영상 검증으로 남긴다.
- DepthOnly/DepthNormals는 같은 RevealAlpha를 부른다. 투명 veil의 Forward는 ZWrite0, opaque shell은 ZWrite1이다. 실제 depth/normal 출력이 camera color로 새어 나오는지는 현재 cyan 실패와 함께 진단해야 하며 컴파일만으로 통과시키지 않는다.

## 원본 재질 복구·범위

`ReleaseSurface(:742~750)`는 원래 sharedMaterials 배열을 다시 연결한 뒤 자신이 만든 clone/overlay만 파괴한다. 건물의 혼합 slot 원본 참조는 DestroyMaterials의 preserved 배열로 보호한다. OnDisable/OnDestroy는 surface와 RT/material cache를 해제한다. 정적 복구 경로에서 원본 에셋을 직접 변경하는 코드는 찾지 못했다.

추가 architecture 검색은 BlenderExpansion의 Shell/Roof와 retained shell 등으로 제한하고 Floor/colliderOnly/renderStain을 제외한다. 의도와 관계없는 전역 시야·전역 outline·캐릭터 shader를 바꾸는 경로는4개 patch에 없다. 실제 범위가 국소 aperture로 유지되는지는 첫 prototype에서 실패했으므로 수정 후 반드시 다시 봐야 한다.

## 성능: 구조상 비용, 측정 전 보류

- ActorMask는 활성 reveal이 있을 때에만 actor renderer를 다시 그린다. 이번 원문은36개 submesh draw를 기록했다. half-resolution RGFloat+depth RT를 보유하며 resize 시 재생성한다. Release 경로는 있다.
- RevealWeight는 중심1+3개 ring×8방향으로 **fragment당 최대25개 mask sample**을 수행한다. mask 밖의 화면 bounding rectangle을 먼저 거르는 조기 반환은 없다. 선택된 큰 건물 mesh의 opaque/veil 및 depth/normal pass에서 비용이 중첩될 수 있다. 국소 결과 이미지가 곧 국소 GPU 비용이라는 뜻은 아니다.
- 건물 선택도 cached vertices/triangles에 대한 여러 CPU ray/triangle 교차를 매 프레임 수행한다. 새 Shell/Roof 범위와 큰 mesh에서 이전보다 비용이 늘 수 있다. mesh/material cache가 있으므로 매 프레임 모두 새로 만드는 구조와는 구분한다.
- 이 비용들은 코드로 확인되지만 실제 ms 증가나 FPS 실패는 아직 측정하지 않았다. 동일 view·해상도·프레임 수의 전후 CPU/GPU 계측 후 판단한다.

## 검토 종료 조건

## 후속 원인 후보: Editor variant loading fallback

원소유 agent가 찾은 local URP `Shaders/Utils/FallbackLoading.shader:61`을 이 담당도 직접 읽었다. 출력은 정확히 `float4(0,1,1,1)`이며 오류용 magenta와 다른 **로딩 중 cyan**이다. 따라서 shader supported/errorFalse이면서 첫 실제 화면이 균일 cyan인 상황을 설명하는 구체적 후보가 있다. RT/viewport 또는 flip을 확정 원인으로 단정했던 것이 아니며, 이 loading 경로를 먼저 분리하는 것이 타당하다.

메인/소유 agent는 iteration03에서 두 전용 shader의 HLSLPROGRAM4곳에만 `editor_sync_compilation`을 추가했고, 전역 async 설정·outline/renderer feature는 유지했다고 전달했다. 이 담당도 production의4개 pragma를 읽었다. 메인은 W03 원래 색 복원을 보고했으나 독립 이미지 검토는 아직 통지 대기다. 이 해결 소식을 최종 S11 가림·mask UV·여백·성능까지의 통과로 확대하지 않는다. 위 첫 실패 화면·가설·한계는 이전 iteration 기록으로 보존한다.
