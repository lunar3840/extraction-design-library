# 실제 마우스 입력 검증 · 2026-10-23

## 격리와 조건

- SystemsTest /1920×1080 /일반 Play에서 실제 Windows 마우스를 사용했다. 유니티 입력 상태를 가상 장치로 주입하거나 거래 API를 호출한 것을 마우스 성공으로 기록하지 않았다.
- `Library/UnifiedUiEvidence/interactive-1920x1080-9dba46771ec645f3ba60a739b9632653` 전용 저장만 사용했다. 메인 화면의 새 게임→빈 슬롯1→확인 버튼으로 실제 새 세션을 만들었다.
- helper는 전용 저장 경로·세션 소유 검증, Game View 캡처·cleanup만 맡았다. 캡처 명령을 낸 직후 다음 입력이 반영된 화면도 있어 파일 이름은 화면 분류이며 정확한 무입력 순간을 보증하지 않는다.
- `interactive_manifest_1920x1080.txt`:7개 캡처/해상도 검증/Title·noSession cleanup 완료. 실제 버튼 성공 판정은 메인이 창 화면과 대응 PNG를 직접 확인했다.

## 검증하지 못한 범위

- 자동 조작의 Tab/I 키 입력으로 게임 내 전환이 관측되지 않았다. 같은 환경에서 Editor 단축키(Ctrl+O/R)와 마우스는 작동했다. 이 현상의 원인은 확정하지 않았고, 실제 물리 키보드에서 기능이 실패한다고 판정하지 않는다.
- 이 때문에 Tab/I/F/V/R 등의 **native 단축키 성공**은 이번 검증 결과에 포함하지 않는다. 키 처리 생산 코드는 이번 스타일 변경에서 바꾸지 않았다. 파밍 F단발/리그V/자동장전 등의 현재 계약은 기존 소스 보존·순수 모델 검사·API 준비 화면으로 별도 확인했다.
- 열린 파밍창의 더블클릭 전송·장비 해제·드롭·지역 맞교환을 이번 마우스 세션에서 전부 반복하지는 않았다. 해당 거래 모델 검사와 스타일 전후 소스 대조는 통과했지만 이를 native 전체 회귀 성공으로 확대하지 않는다.
- 실제 부상/치료를 이 마우스 세션에 추가 생성하지 않았다. 의료 추천·진행·상태 표시는37화면 자동 경로가 정상 시간/전용 리그 UID로 검증했다.

## 추가 발견

같은 Play에서 기존 결과 안내가 남은 채 새 세션의 로비를 열면 `ResultSummary` 배너가 이름/동료 칩 선택 줄을 덮는 기존 문제를 관측했다. 실제 `after_lobby_1600x900.png`에 이 상태를 보존했다. 이 문제의 후속 표시 위치 수정과 검증은 메인의 최종 보완 기록에 별도로 남긴다.

마우스 세션 cleanup 후 일반 저장 경로와 설정을 복구했고, 별도1600×900 화면 검증을 마친 뒤 Play를 명시 종료했다. 원래 v08/Edit/dirtyFalse/FullHD로 복구했으며, 캐릭터 담당에게 명시 반환하기 전 pending request0·fixture소유0을 확인했다.
