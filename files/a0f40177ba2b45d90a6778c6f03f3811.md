# Editor Play timing increase: read-only code review

The actual extra21 Game pair reports show a consistent Editor Play timing increase after production. The paired median change in `editorMedianMs` is **+19.354 ms** (0/21 views improved), and the paired median change in `frameCpuMedianMs` is **+19.204 ms**. The paired GPU median change is **−0.025 ms**; draw calls rise by a paired median 19, while reported scene triangles fall by a paired median 288,111. The base36 cohort, captured from the same saved production state, has a paired editor median change of **−0.282 ms** (22/36 improved). These are report observations, not a proved cause or standalone-build FPS result. Raw report hashes and pairing conditions are recorded in `FINAL_GAME57_TECHNICAL_READBACK.md`.

## What the source shows

- The `Sample()` block in `extra_before_v2/StageAMapIvyRolloutExtraBeforePlay.cs` and `extra_after_v2/StageAMapIvyRolloutExtraAfterPlay.cs` is byte-identical. Both sample `Time.unscaledDeltaTime`, `FrameTimingManager`, `UnityStats.drawCalls` and `UnityStats.triangles` for 90 frames at every pose. Their `Poll()` blocks are also byte-identical. The extra-after `FindObjectsByType<Renderer>` source lookup runs in `Settle()` once per pose before the 90-frame sample, not inside `Sample()`. Image SHA work occurs after sampling in `Confirm()`, and full asset checks occur at Start/Finish. There is no obvious changed per-sample operation in these two capture classes that alone explains +19 ms.
- The current `SurfaceIvyInstance.LateUpdate()` checks source visibility at most once every 0.20 seconds per marker. Its `RefreshVisibility()` inspects up to 64 non-null source renderers and usually stops at the first visible source. It updates generated renderer enabled states only when the visibility result changes. The added 17 markers increase work, but this path is throttled.
- `AMapRuinIvyRevealBinding.LateUpdate()` runs on each marker every frame. Its `SourceIsInV33Reveal()` can traverse every source renderer and each renderer's `sharedMaterials`, checking shader names, until it finds a reveal shader. The 17 approved extra markers bind **336 source renderer references** in the approved register. This is a plausible CPU/Editor allocation contributor when no early reveal-shader match occurs, but the reports do not contain a profiler breakdown. Original A33 bindings and other world work also remain active. The source was read only; no toggle or profiler capture has been run.
- The after capture had a different set of installed Editor helper classes from the original before capture. Inactive helpers have `EditorApplication.update` subscribers that check SessionState and return. The isolated cost of this Editor setup difference was not measured. `Time.unscaledDeltaTime` and Editor frame timing can include such work and other Editor variability.

## Interpretation and next measurement boundary

The identical per-sample capture code, near-zero paired GPU median change and larger paired CPU change make CPU-side work or Editor overhead reasonable hypotheses. They do **not** identify `AMapRuinIvyRevealBinding`, the new meshes, or the editor as the cause. The extra21 and base36 cameras differ, so their absolute timing levels should not be compared as if they were the same scene. A single controlled saved-scene Editor Profiler CPU Timeline capture at a frozen extra pose, with a matched baseline and an explicit Play-only toggle if the main owner judges it safe, would be needed to separate binding cost from capture/editor overhead. Any toggle must restore original source and ivy states and produce its own raw receipt. Until then this remains an unresolved performance concern, not a regression diagnosis or release-performance verdict.
