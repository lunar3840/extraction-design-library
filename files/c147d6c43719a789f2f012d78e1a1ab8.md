# 에델 2차 런타임 최적화

사용자 원문: “2차 계획도 이제 진행해봐”. 후속 “뭔데 못해?”는 진행 확인으로 보존하며 별도 구현 회차로 세지 않는다. USER_REQUEST.md와 계획04인 ../edel-runtime-phase2-plan/CHANGE_RECORD.md에 연결한다. 같은 캐릭터 런타임 개선 의도의 구현05 회차이며 새 대표 주제를 만들지 않는다.

## 결과와 남은 문제

동일 입력 Editor 재생에서 CurrentSource 갱신을 포함한 헤어 Step 평균55.0425→53.1037ms, p95 62.0111→60.2403ms로 감소했다. 평균 감소는1.9388ms/3.52237%다. 기존 검사량·관찰된 결과가 일치하는 두 후보만 채택했다. 준비 비용을 늘리던 최초 eager 후보는 제외하고 실제 검사한 삼각형만 준비하는 방식으로 바꿨다.

렉을 크게 해소하거나 전체 게임 FPS가 개선됐다고 확정한 결과는 아니다. 해당 CPU 경로가 여전히 약53ms로 크고 초기 제안의2ms 목표는 미달이다. 원본/후보 Development Player도 실제 빌드·실행했지만 별도 AI/시간 조건의 hidden-window 실행이며 Render/GPU 계측은 invalid였다. Native frame 시간이나 이들의 비율을 사용자 게임 FPS 개선률로 쓰지 않는다.

후속 사용자 지시의 땋은 머리 꼬임과 팔 얼룩 음영은 이번 최적화가 해결한 문제가 아니다. 원본 코드 복원 진단 컷에서도 보였으며 캐릭터 담당이 별도 원인 분석·수정을 이어간다. 이전 헤어·파지 REVIEW 및 미완료 상태를 최적화 검증으로 완료 승격하지 않는다.

## 변경 전 상태와 역할

before_editor.png는 실제 수정 전 A씬 편집 화면이다. backup/의 Current3B945AA1…, HeadBAD7CBBD…, Hair32183682… 및 BodySurface 원본을 보존했다. before_results.json/before_frozen.png/before_movement.png는 이 원본에서 새로 실행한 기준값이다. 이전1차 이미지를 이번 before로 사용하지 않았다.

메인이 공유 Unity/실행/통합을 맡고 GPT-6 Sol high 제작자는 거리 Current/HeadSource와 Braid Hair를 별도 staging에서 제작했다. 별도 GPT-6 Sol high 검토자는 원본·후보·원자료를 독립 확인했다. 캐릭터/UI 담당의 명시 반환 후 시작했다. W10 한동 샘플 담당과도 조율했다.

변경 전에는 같은 거리 쌍에서 삼각형 변과 길이를 반복 계산하고, 땋은 머리 후보마다 같은 source 방향/회전/분류/제약 상한을 다시 읽었다. 기존 BVH·nearest seed·거리 캐시와 후보 탐색이 있으므로 이를 새 기능처럼 다시 만들지 않았다.

## 실제 채택 변경

- CurrentSourceClearanceFieldBudget.cs: 기존 Apply/Distance/BVH/seed/판정 순서를 유지한다. source 형상의 불변 변 벡터·길이를 준비하고, body/weapon 삼각형은 실제 DistancePair 첫 접근 때만 준비해 Part epoch가 같은 동안 재사용한다. Refit는 원래 점·bounds·BVH·epoch를 갱신하며 epoch 변경이 준비 데이터 무효화 키다. preparedEpoch는 -1로 초기화한다.
- HeadSourceClearanceFieldBudget.cs: 원래 TriangleDistanceSquared 함수는 유지하고 Current가 사용하는 준비 데이터 overload를 추가했다. 여섯 교차 판정·여섯 점/면 거리·아홉 모서리 거리 및 Min/early-zero 순서를 유지한다. Head Prepare 자체를 최적화한 것으로 표시하지 않는다.
- SdHairCollisionMotion.cs: 한 번의 동기식 SolveBraidSurface 안에서 변하지 않는 segmented 분류·원본 방향/회전·길이·상향/통로 상한을 재사용한다. 모든 후보·검사·점수·선택 순서를 유지하고 solve 종료 시 비활성화한다. source 입력이 solve 동안 불변이라는 조건은 Editor oracle로 사용 지점마다 대조했다.

Editor 전용 독립 reference/oracle 스위치는 원래 수식을 호출하거나 매 사용값을 대조한다. 거리 oracle은 원본 좌표와 결과 float의 raw bits를 비교한다. Braid oracle의 mismatch fallback은 성공으로 숨기지 않고 mismatch 누적0을 통과 조건으로 삼았다. 1차 Current bind-local 캐시는 양쪽 모드에서 유지한다.

모델·재질·UV·머리색·허용치·갱신 주기·후보 수·게임 동선·카메라·조명은 직접 수정하지 않았다. BodySurfaceProjector/SdWeaponPose/EdelIndexSkinBinding도 그대로다. 이전에 반려했던 score 정점/face 캐시는 재도입하지 않았다. 최종3파일의 사본은 adopted/와 FINAL_SOURCE_HASHES.json에 있다. 이후 캐릭터 담당이 별도 수정하므로 이 해시는 이번 검증·반환 시점의 기준이다.

## 동일 입력 CPU 및 결과 검사

paired_results.json / MATCHED_SUMMARY.json / FINAL_MEASUREMENTS.json이 최종 근거다. 실제 이동·조준·사격 소스 포즈80개를 같은 Play에서 원본→개선→개선→원본→원본→개선 각80step 재생했다. 각 회차 첫10step 제외, 모드별210표본이다. 바깥 Stopwatch는 Current BeginFrame을 포함한 전체 Step을 재며 입력 적용·해시·파일 저장·Bind는 제외한다. oracle 회차는 성능 통계에서 뺐다.

기준 대비480쌍의 지문과 관찰 work counters 불일치0이다. 최종 거리 oracle375,078회, Braid110,503회 대조 불일치0이다. 지문에는 정점·본 TRS·표정·선택 witness/proxy/bary/mobility와 Head/Current budget·거리/nearest cache·part seed/epoch 등이 포함된다. 모든 trial별 valid/depth/normal 및 BVH 방문 이벤트를 빠짐없이 기록한 ordered trace는 아니므로 전체 탐색의 모든 항목을 독립 검증했다고 주장하지 않는다.

후보별 자료도 분리했다. paired_distance는 반려된 eager 준비 후보로57.1515→55.6560ms였으나 live CurrentRefresh가11.41→13.50ms로 늘어 순이득 상쇄 우려가 있었다. paired_distance_v2는 실제 사용 삼각형만 준비하여55.1362→54.5010ms, oracle371,553회 불일치0이었다. 평균 pair4,644회 중 준비392.5개이며 builds<=calls, reference builds0을 확인했다. paired_braid는61.3328→60.8627ms의 작은 감소다. 서로 다른 trace/실행이므로 개별 감소율을 합산하지 않는다.

세린·리브·유이의 최종 조합6포즈 회귀도 결과/카운터/oracle 불일치0이다. 유이 시간은22.2408→22.4101ms로 소폭 늘었으나6포즈는 대표 성능 벤치마크가 아니다. 모든 캐릭터가 빨라졌다고 일반화하지 않는다.

## 읽기 보호 메시 보강과 메모리 한계

초기 검증 도구의 sharedMesh.vertices는 읽기 보호된 Edel_SkinnedVest에서 빈 배열과 Unity 로그를 반환했다. 따라서 초기 full 지문 및 이전1차의 같은 방식 자료는 해당 조끼 정점을 포함하지 않는다. 이전 수치를 모든 메시 완전 검증으로 해석하지 않는다. 도구를 고쳐 false 지문은 기존 빈 배열 형식을 유지하며 경고를 피하고, full 지문은 읽기 불가 메시를 재사용 Mesh에 BakeMesh한 정점까지 해시했다. 에셋 Read/Write 설정은 변경하지 않았다.

새 paired_quality 및 세린/리브/유이 quality 자료는 각6포즈×원본/개선/oracle다. Edel의 읽기 보호 조끼6,041정점을 포함했고 네 캐릭터 각각12비교쌍의 지문·work 불일치0이었다. 거리 대조는28,578/168,844/967/2,388회 모두 불일치0, Edel Braid9,073회 불일치0이다. 플레이어 하위 메시·본·캐시 결과의 범위이며 외부 계층 장비까지 전부 검사했다고 넓히지 않는다.

GC.GetAllocatedBytesForCurrentThread는 명시64KiB 배열 할당 검정에서 delta0이어서 invalid로 판정했다. 초기0값을 무할당 증거로 사용하지 않는다. 정상 게임 구간의 native GC recorder는 유효했지만 전체 프레임 값이라 캐시 단독 비용을 분리 입증하지 않는다. live 평균245,632→158,749B/frame, Player149,282→52,217B/frame 관찰은 AI/시간/작업량 차이와 함께 해석한다. 이름 등 반복 source 조회 감소가 관련될 수 있으나 이 차이 전부를 후보 효과로 귀속하지 않는다.

Editor의 Edel 추가 준비 배열 payload는4,007,284B(Part3,729,000+epoch149,160+source128,900+Braid224)이며 헤더·기타 객체 오버헤드는 제외한다. Editor oracle용 원본 점이 포함된 크기다. 초기 Bind/첫 배열 준비 비용과 재바인드 heap 변동은 별도 원자료에 보존했고 정상 프레임과 섞지 않는다. 아주 장기 실행·모든 장비/표정 조합·epoch overflow 범위는 미검증이다.

## 실제 A맵과 Development Player

before/final의 실제 A맵 입력은 각각360프레임(40warm+80측정×3), 사격12회·재장전3회다. 최종 고정20step 지문은 원본과 exact다. live frame 평균74.1844→75.4452ms로 실제 전체 프레임 개선은 입증하지 못했다. AI/날씨/실제 애니메이션 시간이 다르므로 이 비율을 후보의 인과적 손익으로 정하지 않는다.

실제 원본3파일로 되돌려 reference 개발 빌드를 만들었고 후보3파일 candidate도 별도 빌드했다. 각 고유 timestamp 산출물의 SOURCE_HASHES.txt와 LAUNCH.json, PLAYER_reference_RESULT.json/PLAYER_candidate_RESULT.json이 소스·exe·실행을 연결한다. 두 빌드의 테스트 driver 해시는 같다. A씬만 BuildPlayerOptions로 지정했고 EditorBuildSettings/품질 설정을 직접 변경하지 않았다.

두 Player 모두 임시 profile 경로,360행·12발·재장전3회·exit0을 확인했다. 정상 사용자 슬롯을 사용하지 않았다. 각 회차40warm 제외240표본의 frame 평균은 reference96.5305/candidate83.7767ms, 헤어 내부 Step68.2963/57.8868ms였다. 각기 다른 live 작업량·시간이고 hidden window이므로 이 차이를 동일 입력 FPS 개선률로 보고하지 않는다. Main/GC는 valid, Render/GPU timing은 invalid다. Player ReadPixels는 drawing-frame 밖 경고가 있어 그 PNG는 시각 검증에서 제외했다. 원시 로그·실행 파일은 공개 수집하지 않는다.

## 독립 검토·정리·반환

staging/review/FINAL_REVIEW.md는 live source 대신 adopted 사본을 읽고 소스 해시,480쌍/추가 quality, Player provenance·입력·임시 저장·계측 제한과 사진3쌍을 재검사했다. 메인이 최종 보고를 읽고 결과 동일성 및3.52% CPU 감소라는 한정 범위로 채택했다. 전체 FPS/모든 장비/기존 외형 문제 해결 판정은 하지 않는다.

임시3개 C# 도구와 meta는 제거하고 VALIDATION_TOOL.cs.txt/BUILD_PROBE.cs.txt/BUILD_TOOL.cs.txt로 보존했다. FINAL_REFRESH.txt 및 after_editor.png에서 원래 A씬 playing=False·dirty=False를 확인하고22:03:40/41 Runtime/Editor 재컴파일을 확인했다. 기존 refresh 도구가 고정 경로에 쓴 로그는 원본 보관본으로 복원했다. 첫 legacy invoke는 namespace 불일치로 빌드를 시작하지 못했고 실패 로그를 BUILD_INVOKE_FAILED_NAMESPACE.txt에 보존한 뒤 자체 요청 경로로 고쳤다. 실제 빌드 성공은 이후 결과만 사용한다.

공유 Unity/합의 소스는 캐릭터·UI·W10 담당에게 명시 반환했다. 동시 다음 점유 충돌은 Edel 진단→명시 반환 후 W10 순서로 다시 조율했고 두 담당이 동시 실행 없음을 확인했다. 메인은 반환 후 Unity/Assets를 더 수정하지 않는다. 이후 장면/코드 변화는 각 담당의 후속 작업이며 이 검증 종료 상태와 구분한다.

## 라이브러리

원문·전후·최종 실측·독립 검토의 준비와 실제 공개 게시를 구분한다. LIBRARY_EVIDENCE.json의 문서/정상 게임·Editor4이미지만 선택한다. 대용량 build binary, raw trace/log, 잘못된/진단용 노출 사진과 임시 stage는 공개 대상에서 제외하고 로컬 보존한다.

초기 게시 대기 당시 기록(아래 실제 게시로 해소): 메인 최종 정리 후 기존 MD 담당의 단일 게시 순서로05를 기존 주제 다음 회차에 붙인다. 이전02/03/04는 이미 인증 복구 후 게시된 상태이며 이번05는 별도로 실제 원문·이미지·주제/분류·ledger 공개 재조회까지 확인해야 한다. 준비 표시만으로 게시 완료라고 말하지 않는다.

## 실제 라이브러리 게시 결과

- 게시 담당이 기존 네 캐릭터 주제/캐릭터/캐릭터 공통/변경 결과/2026-10-26-05를 유지하여 이 회차만 증분 수집했다. 허용 문서7개·정상 게임/Editor 이미지4개·전후2쌍을 연결했다. 잘못된 캡처·Player framebuffer·base avatar 근접 진단·대용량 binary/raw trace/log/staging asset은 수집하지 않았다.
- 2026-10-26T22:24:19+09:00 기준 선택 자료11개·썸네일3개·색인에 대해 익명 HTTP200/SHA256 일치를 확인했다. 게시 장부에도 원문·선택 이미지가 모두 포함됐다. 인증 없는 업로드는401로 보호된다. 기존 세션 인증을 사용했고 키 교체·환경 변경·화면 소스 배포는 하지 않았다.
- 기존1072항목·29게시기록·기존 원문 매핑을 보존했고 총1073항목·307주제·준비 게시30기록이 됐다. 회차06과 W10 등 다른 미완료 기록은 포함하지 않았다. 게시 완료 표시도 다시 수집·게시하여 동기화한 뒤 최종 원문/index/ledger 해시와 실제 화면 확인은 `PUBLICATION_VERIFICATION.json`에 남긴다.
- 채택 소스는 현live파일을 읽거나 수정하지 않고 `adopted/`의 고정3사본을 `FINAL_SOURCE_HASHES.json`과 대조했다. 사본 자체는 허용목록 밖으로 로컬에 보존한다. 원문·실측·독립 검토의 관찰 범위를 바꾸지 않았고, 게시 과정의 Unity/빌드/새 성능 실험은0이다. 3.52% 동일 입력 CPU 감소를 전체 FPS 개선·GC 무할당·기존 꼬임/팔 음영 해결로 승격하지 않았다.
- 갱신 전 원문은 `PUBLICATION_SOURCE_BEFORE_COLLECTION.md`에 보존했다. 라이브러리 게시 전후는 `before_library_publish.png`/`after_library_publish.png`, 상세 확인은 `after_library_detail.png`에 저장한다. 브라우저 원 캡처 JPEG도 보존하며 PNG는 같은 화면의 형식 변환본이다. 이 캡처를 게임 구현 전후 증빙으로 재사용하지 않는다.
