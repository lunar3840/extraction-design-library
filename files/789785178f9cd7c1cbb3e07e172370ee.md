## 검토 기준: 제안, 아직 실행 결과 아님

1. 외관뿐 아니라 **원래 몸체 메시의 실제 형상 변화**를 확인한다. 원본/새 폐차 차체와 S06 shell/roof 몸체의 vertex·triangle 수, bounds, fingerprint를 분리 기록한다. 파편만 새 메시로 붙고 몸체가 같으면 통과하지 않는다.
2. 절단면은 두께와 재료가 있고 윤곽이 불규칙해야 한다. 건물은 빠진 면, 깨진 가장자리, 지붕 처짐/꺾인 부재 중 해당 계획된 변화가 렌더에서 보여야 한다. 규칙적인 상자 더미로 형상을 흉내 낸 결과는 보류한다.
3. 낙하 파편은 크기와 방향이 달라야 하며 지면 접촉·출처 위치가 납득되어야 한다. 부유, 과한 관통, 같은 면 중복으로 인한 z-fighting을 사선·상단·세부 카메라에서 검토한다.
4. 주요 문·창과 원래 지붕 구멍을 열어 둔다. 덩굴은 분명히 풍성해지되 파손 단면, 출입구, 기존 개구부와 건물 고유 실루엣을 가리지 않는다.
5. S06 석고·벽돌·금속·유리, 폐차 차체·유리·타이어의 색과 재료 구별을 유지한다. 원본/신규 재료 슬롯과 색 설정을 함께 대조한다.
6. 원본 메시/재료/씬/AI/renderer/조명 파일의 해시는 작업 전후 동일해야 한다. 새 프리팹·재료·메시만 저장하고 새 콜라이더 수는 0으로 확인한다.
7. 새 시안에서 bake→reimport→prefab reload 후 몸체 메시·재료·덩굴 참조가 유지되는지 확인한다. 덩굴 반복 preview/clear는 중복 root와 죽은 renderer 참조를 남기면 안 된다.
8. 폐차와 건물 각각 같은 카메라의 before/after 사선·상단·필요 상세를 비교하고, 두 시안을 동시에 볼 수 있는 합성 이미지도 확인한다. 실제 게임 화면을 확인하지 않았다면 별도 시안으로만 보고한다.
9. **범용 도구 추가 게이트:** building/vehicle/prop 최소 3종, non-readable 원본 mesh, 계층 renderer, 회전·비균일·음수 scale에서 원본 참조·transform·render state를 보존한 채 복제본만 변경해야 한다. `kind / seed / damage / debrisBudget / triangleBudget` 입력과 같은 seed 재현·다른 seed 변화, 예산 준수, 예외별 오류가 기록되어야 한다.
10. 선택된 scene object와 asset target 양쪽에서 Preview가 원본을 건드리지 않고 분리되어야 한다. Batch는 각 대상의 fresh Preview, 재실행/Clear 정리, 중간 실패 후 다른 대상 계속 처리, 대상별 성공/실패 보고를 확인한다. 저장된 신규 mesh/material/prefab은 재 import/reopen 후 동일하게 남아야 한다. UI 현재 상태 창과 두 실제 데모도 확인한다.

## 범용 코드 staging 정적 검토 (실행 확인 아님)

`staging/building/RuinGeometryEngine.cs`의 첫 범용 초안을 읽었다. `RuinIvyRecipes.cs`의 bounded building/vehicle/prop 설정과 별도 `RuinIvyRecipesValidation.cs`도 읽었다. 이 절은 소스에서 보이는 위험이며 Unity 실행 PASS/FAIL이 아니다.

- `RuinGeometryEngine.ReadMesh/CutRenderer`는 새 메시를 position/normal/UV0로 재구성한다. 원본 tangent, UV2/lightmap, vertex color 등 다른 속성은 이전되지 않는다. 원본 머티리얼/normal map/광원에서 차이가 나지 않는지 확인하거나 필요한 속성을 보존해야 한다.
- 새 `MeshRenderer`에는 shadow casting, receive shadows, light/reflection probe 사용만 복사한다. layer, lightmapIndex/ScaleOffset, renderingLayerMask, material property block 등은 현재 복제 경로에 보이지 않는다. 기존 renderer 상태와 결과 renderer 상태를 비교할 필요가 있다.
- `triangleBudget`은 1,000 아래 입력을 1,000으로 올리고 source triangle 누적에만 적용된다. cap 및 debris 포함 최종 triangles를 예산 안으로 제한하지 않는다. UI가 이 숫자를 결과 예산으로 설명한다면 충돌한다.
- `Apply`는 작업 사본의 원본 renderer를 비활성화한다. 중간 실패 후 복구, 재 Preview와 Clear에서 중복 생성물·꺼진 renderer가 남지 않는지 실제 실행해야 한다.
- `RuinIvyRecipesValidation`은 vehicle/building/prop 샘플에서 생성 양수 확인을 제안하나 현재 Unity 실행 보고가 없다. 잎 화면 점유, 개구부 유지, 일반 asset에 적용 가능한 분류는 별도 시각/기능 확인이 필요하다.

### 범용 엔진 후속 소스 정정과 남은 위험

제작자는 같은 `RuinGeometryEngine.cs`를 갱신했다. position/normal/UV0뿐 아니라 tangent·UV1~3·color 읽기/보간/출력, 추가 renderer 상태와 property block 복사, 신규 root 추적, source mesh fingerprint, 최종 triangle 예산 및 rollback이 **소스상 추가됨**을 확인했다. 따라서 위 처음 세 항목은 첫 초안의 위험 기록이며 현재 코드에서 상당 부분 보완됐다. 실제 Unity 컴파일·재열기·픽셀/transform 결과는 아직 확인하지 않았다.

남은 정적 우려: 새 mesh child를 원래 renderer 아래가 아니라 생성 root 컨테이너 아래에 놓고 `relative.rotation`과 `relative.lossyScale`로 상대행렬을 분해한다. 중첩 회전과 비균일/음수 scale이 합쳐진 행렬에는 shear/반사가 있어 단순 TRS 재조합이 원래 vertex world 위치를 정확히 재현하지 못할 수 있다. 명시 수용 기준인 rotated/nonuniform/negativeScale의 **복합 케이스**를 실제 실행해 원본 렌더 표면과 생성 표면의 좌표·노멀을 대조해야 한다. 제작자와 메인에 알렸다.

제작자는 이를 다시 수정해 renderer→root 전체 행렬을 새 vertex에 직접 적용하고 inverse-transpose normal, 반사면 triangle winding과 tangent.w를 처리했다. 이로써 위 행렬 분해 위험은 **소스상 해소**됐다. 실제 Unity 복합 scale 결과는 여전히 대기다. 새 `DamageField.AdaptToSurface`는 building 외 첫 100tri 초과 renderer를 기준으로 cut 중심을 옮길 수 있으므로, glass/decal이 먼저 오는 다중 renderer 차량/소품에서 몸체가 아닌 표면을 고르지 않는지 확인할 필요가 있다.

제작자는 body/chassis/shell/frame 우선, glass/decal/stain/ivy 제외, wheel/tire 등 감점으로 `AdaptToSurface` 대상 선정을 수정했다. 이 위험도 소스상 보완됐고 실제 다중 renderer 시험이 남는다.

## 독립 실행 harness와 통합 API 검토

메인이 확정한 `RuinAuthoring.Preview/Bake/Clear`, `RuinPreview`, `RuinToolSettings` 계약에 맞춰 `staging/validation/RuinToolValidation.cs`를 작성했다. `ValidateCore()`는 실제 차량/S06 외벽/소품 3종, 같은 씨앗 재현, 작은 삼각형 예산 rollback, 중첩 회전·음수/비균일 scale의 non-readable scene fixture를 검사한다. `ValidateBatchLifecycle()`는 세 대상 동시 preview, 잘못된 대상 1개 오류 격리, 같은 대상 재 Preview, Clear 반복, 원본 의존 해시를 검사한다. `ValidatePersistence()`는 차량에 weather+ivy까지 결합해 Bake→reimport 뒤 recipe/seed, 활성 생성 mesh의 vertex/index fingerprint, collider0를 검사한다. 메인이 Unity에 반입·실행하기 전 상태이며 **실행 결과 아님**이다.

`RuinAuthoring.cs`에서 **실행 전 수정이 필요한 정적 위험**을 발견했다. scene source가 비영속 mesh/material/texture를 공유하는 경우 `Instantiate(source)`한 copy의 `Track(context,copy)`가 그 공유 자원을 수집하고 `Clear`에서 `DestroyImmediate`한다. 그러면 원본 scene object의 자원이 함께 소멸할 수 있다. harness의 non-readable scene fixture가 이 수명 문제를 직접 검사한다. 원본 source의 비영속 의존성을 수집 대상에서 제외하거나 scene clone이 별도 사본을 갖도록 고쳐야 한다고 메인에 전달했다.

메인은 `protectedSourceResources` 사전 수집, scene 비영속 mesh/material/texture의 도구 소유 사본, component/재료 texture 참조 치환, 원본 자원의 Track 제외를 추가했다. 정적 소스에서 이 수정 경로를 확인했다. 원본 fixture가 preview→Clear 후 mesh/material/transform을 유지하는지 Unity 실행 결과를 기다린다. harness의 `ValidateCore`, `ValidateBatchLifecycle`, `ValidatePersistence`, `Execute` API는 동결해 메인에 인계했다.

### 첫 Unity 실행 정정

`COMMAND_validate_205952.txt`를 읽었다. Play off, A맵 씬 dirty false 전후는 기록됐으나 전체 검증은 `Fixture cut mesh missing`으로 중단됐다. 원인은 독립 harness가 GameObject 이름에서 `_Cut`을 찾은 실수다. 생성 엔진은 GameObject를 `__RuinGenerated_Body`, mesh를 `..._Cut`로 명명한다. staging harness를 `x.sharedMesh.name.Contains("_Cut")`으로 고쳤다. 이 실패는 엔진 파손 메시 부재를 입증하지 않는다. 제어 흐름상 앞선 실제 car/building/prop·seed·budget assert는 이 실행에서 해당 예외 전까지 통과했지만, 실행 로그에 부분 수치가 남지 않아 최종 PASS로 기록하지 않는다. ## 선택 기능 추가 게이트: 실행 전 코드 검토와 제안

`RuinAuthoring.cs` 및 `SurfaceRuinWindow.cs`의 현재 production 소스를 읽었다. UI 세부 설정에 `generateStaticColliders` 토글이 있으며, Preview는 켜졌을 때 copy의 기존 Collider를 제거한 뒤 활성 MeshRenderer와 MeshFilter에 비볼록 MeshCollider를 붙이고 Ivy/ShadowOnly renderer를 제외한다. 꺼졌을 때 copy의 Collider를 제거한다. 이 동작은 위 21:32 기본값 OFF 검증에서만 확인됐고 **ON의 Bake 재열기는 미검증**이다. 또한 scene source가 parent 아래 있을 때 `Instantiate(source, carrier.transform)` 후 copy를 parent에서 떼는 경로가 원래 parent world 행렬을 보존하는지 코드만으로 확정할 수 없다. 기존 중첩 변환 fixture는 선택 root 자체의 자식 hierarchy 검사였으며 **선택 root의 외부 parent**는 검증하지 않았다.

독립 harness에 딱 두 선택 게이트를 추가했다. `OPTIONAL PARENTED SCENE TARGET`은 회전·비균일·반사 scale parent 아래 scene source와 preview의 몸체 8개 world vertex 위치를 1mm 이내 대조하며, Clear 뒤 원본 parent·mesh·좌표를 확인한다. `OPTIONAL STATIC COLLIDERS`는 실제 S06 건물에 ivy와 정적 collider 옵션을 함께 켜서 활성 비-Ivy renderer당 비볼록 MeshCollider와 같은 mesh 참조를 Preview와 Bake→reimport 양쪽에서 확인하고 원본 asset 해시가 유지되는지 본다. S06의 collider-only proxy renderer가 Preview copy에서 꺼져 있고 새 Collider가 그 proxy/ivy에 붙지 않는지도 본다. **이 두 추가 테스트는 아직 메인의 Unity 실행 전**이다. 이전 기능 게이트 `VALIDATION_213247.txt RESULT PASS`는 당시 검증한 범위에서 유효하며 새 항목의 결과를 소급해 주장하지 않는다.
