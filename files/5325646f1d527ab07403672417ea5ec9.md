# W10 Blender 창고 한 동: 독립 검증 계획

## 범위와 상태

이 폴더의 `W10BlenderSampleValidation.cs`는 Unity `Assets/Escape/Editor/`에 복사하여 컴파일할 **스테이징 소스**다. 이 담당은 공유 Unity 편집기, Blender, 장면, 프리팹, 원본 코드 및 브리지를 실행하거나 수정하지 않았다. 현 시점의 결과는 설계·소스 검토이며 실제 Unity 통과 결과가 아니다. `W10_VALIDATION_CONTRACT.template.json`의 빈 값은 임의 좌표로 채우지 않는다.

검증 대상은 D09 원본 조사에 기록된 `W10` 단일 건물이다. 전체 69동 외관 통과, 전체 맵 밸런스 변경, 스폰 규칙 변경의 판정으로 사용하지 않는다.

## 원본 계약과 적용 담당 입력

- 원본: `outputs/change_records/2026-10-13/a-map-concept-rebuild-d09/BUILDING_SURVEY.json`의 `W10`. `Logistics/ExportInspection`, owner `EnclosuresV33_ConnectedFacilities/Buildings/W10`, 지붕 cutaway `.../Visual/Generated/Override_ENV11_BUILDING_WM_06/RoofCutaway`, 원점 `(-140, 1.0270169, -46)`, 약 4도 Y 회전, 외곽 `22.9964 × 14.0043m`.
- 원본 문 `metadata_0`은 local Z+, world 밖 `(-139.4118, .9631, -37.6185)`, 안 `(-139.6078, 1.0800, -40.4116)`; `metadata_1`은 local Z-, 밖 `(-140.5882, .8548, -54.3815)`, 안 `(-140.3922, 1.0800, -51.5884)`. 두 문 모두 조사 폭 3.4m, 높이 3.1m. 이 좌표는 기존 D09 조사 기준이며 새 모델의 실제 메시 개구·충돌과 다시 비교한다.
- 적용 담당은 **적용 전에** 메인이 보관한 전 상태 이미지와 별도로 `CaptureBaseline():string`을 한 번 실행하여 `W10_BEFORE_STATE.json`을 만든다. 이미 존재하면 덮어쓰기를 거부한다. 이때 `StageALootSpawner.ValidateGeometry(map)`의 전체 50개 사전 배치 검사를 실행하고 W10 두 결과의 바닥·접근점·회전·지지 충돌체·출입문을 저장한다. 보상 생성이나 밸런스 추첨은 실행하지 않는다. 장면은 저장하지 않는다.
- 적용 담당은 샘플 적용 후 템플릿을 복사해 `W10_VALIDATION_CONTRACT.json`에 현재 맵 루트 기준 **정확한** facade/roof/interior Transform 경로, inspection room 문 양쪽 지점·폭, 수정이 허용된 원본 W10 스냅샷 키, 최소 네 개의 시각 렌더러/충돌체 일대일 대응 경로를 기록한다. 계획 루트는 W10 owner 아래 `W10_BlenderSample_Shell`, 같은 owner 아래 `W10_BlenderSample_Interior`, 기존 `RoofCutaway` 아래 `W10_BlenderSample_Roof`다. 키 형식은 `T|경로`, `R|경로|컴포넌트번호`, `C|경로|컴포넌트번호`다. 허용 목록에는 실제 변화한 기존 항목만 넣는다. 기존 D09 facade/roof의 `GameObject.activeSelf=false`도 명시적 허용 대상이며, 자식 `enabled` 상태까지 일괄 변경하지 않는다.
- 메인은 실제 소스 경로와 상자 접근점을 확인한 후, 스테이징 소스를 Unity `Assets/Escape/Editor/`에 반영하고 컴파일 진단을 읽는다. 호출은 `Escape.EditorTools.W10BlenderSampleValidation.Run(): string`. 결과 문자열은 같은 폴더의 `W10_VALIDATION.txt`에도 기록된다.

## 자동 검증 게이트

1. 전 스냅샷과 현재 맵의 scene/map 일치; W10 밖 원본 hierarchy, Transform, 활성 상태, 렌더러/재질/메시 참조, 콜라이더 상태·형상 및 신규 객체 범위 비교. W10 기존 컴포넌트의 변화는 명시한 키만 허용한다. 이 비교는 기존 B1–B4, R1–R8, 출구, relay 등 맵 하위 지점의 보존도 포함한다.
2. W10 facade/interior/roof 실제 활성 메시·재질 검사와 roof의 기존 cutaway 계층 연결 확인. 지붕이 외부에서 보이고 내부에서 숨겨졌다가 외부에서 복귀하는지 임시 표시 전환 후 원래 renderer enabled 상태로 되돌린다.
3. 조사된 문 두 곳 각각에 대해 너비 중심/양측, 캡슐 반경 0.4m·높이 2m, 2.95m까지의 개구, 지면/문턱 지지, 선형 시야를 검사한다. 충돌체 ray와 W10 새 FBX의 **읽기 가능한 실제 렌더 삼각형** ray를 각각 검사해 시각 벽만 문을 덮은 경우도 잡는다. `GlassMuted` 슬롯은 투명 시야 재료로 취급한다. 경사·바닥은 이름으로 면제하지 않고 실제 상향 충돌 표면으로 판정한다.
4. `StageALootSpawner.ValidateGeometry(map)`의 W10 두 결과(`loot_w10_shipping`, `loot_w10_weapons`)가 전 상태와 동일한 바닥·접근점·회전·지지 충돌체·출입문을 유지하는지 비교한다. 접근점 바닥·캡슐 공간과 상자 예정 위치까지의 충돌/렌더 삼각형 시야도 검사한다. 시선 높이는 실제 `LootInteractor`의 플레이어 발+1m→상자 바닥+0.4m와 맞춘다. 실제 상자 오브젝트는 Play 중 `Session/A_Loot_Raid/...` 아래 생성되므로 Editor에서 존재한다고 주장하지 않는다.
5. 계약의 시각/충돌 대응 네 쌍 이상을 검사하고, 동결된 Blender `EXPORT_MANIFEST.json`에서 `collisionSuggested=true`로 선언한 **모든 W10 메시**가 같은 개체의 읽기 가능한 렌더 메시와 동일한 `MeshCollider.sharedMesh`를 사용하며 실제 바운드가 일치하는지 검사한다. 선언하지 않은 개체에 예상 외 MeshCollider가 생긴 경우도 실패로 기록한다. 픽셀 정합과 재질 인상은 실제 게임 화면으로 확인한다.
6. 새 inspection room 문 1.6m 개구·문턱·시야·양방향 지역 경로를 검사한다. 새 실내 충돌체가 중앙 보호 통로 및 두 파밍 위치 반경 1.6m의 접근 보호 영역을 침범하는지도 `Physics.OverlapBox`/`Physics.OverlapCapsule`의 **실제 충돌 hit**로 확인한다. 비볼록 MeshCollider에 지원되지 않는 `Collider.ClosestPoint`는 사용하지 않는다.
7. `StageMapRouter.BuildNavigation`으로 충돌 기반 `NavMeshData`를 임시 생성하고 두 기존 문 각각의 양방향 지역 경로와 실내 중심 경로, 두 상자의 실제 사전 배치 경로 및 검사실 문 경로를 검사한다. `finally`에서 임시 NavMesh 인스턴스와 데이터를 제거한다. 소스 장면·오브젝트 위치를 저장하거나 변경하지 않는다.

## 별도 실제 플레이 게이트

Editor의 NavMesh와 물리 query만으로 실제 조작 통행을 확정하지 않는다. `W10BlenderSamplePlayValidation.cs`는 별도의 **스테이징 소스**다. 메인이 공유 Unity 사용 순서를 확보하고 Editor 검증이 통과한 뒤 `Run()`으로 W10만 검사한다. 현재 편집 씬의 `StageScenePreview`가 만든 격리 World와 50개 출격 상자 생성 완료를 기다린다. 실제 `PlayerMotor.Simulate`와 활성 `CharacterController`로 북쪽 밖→북쪽 안→남쪽 안→남쪽 밖의 연속 경로와 역방향, 검사실 문 양방향, W10 두 상자 접근점으로 걷는다. 중간 지점마다 현재 플레이어 위치로 지붕 컷어웨이와 원본 지붕 비활성 상태를 확인한다. 실제 상자의 ID/위치가 사전 배치 결과와 맞는지도 검사한다.

각 상자 앞에서 캐릭터를 바라보게 한 뒤 실제 `LootInteractor.CanOpen` 및 `Open`을 호출하여 거리와 장애물 시야 조건을 통과하고 창이 열리는지 확인한다. 현재 `LootInteractor.CanOpen` 소스에는 캐릭터 방향 자체를 거르는 조건이 없으므로 방향만으로 열림을 보증하는 기능까지 검증했다고 기록하지 않는다. 공개 `LootState.Open`을 직접 호출하지 않는다. 물품 회수, 보스 처치, 적 위협과 생존율 평가는 포함하지 않는다. Play 종료 시 Edit 상태로 돌아가며 사용자 저장 파일과 공유 씬을 저장하지 않는다. `PlayerMotor.Simulate`는 실제 컨트롤러 충돌을 사용하지만 물리 키보드·마우스 입력을 검증하는 방법은 아니다. 각 실행은 새 `play_attempt_XX/`에 로그·스크린샷을 남기며, 이전 시도의 증빙을 덮어쓰지 않는다.

## 판정

`W10_VALIDATION.txt`의 `RESULT PASS`는 계약이 완성되고 해당 Unity Editor 자동 검사 전부가 통과했을 때만 유효하다. `play_attempt_XX/W10_PLAY_VALIDATION.txt`는 별도 판정이며, 컴파일 실패, 전 상태 스냅샷 누락, 실제 Play 게이트 미실행, 전후 게임 이미지 또는 변경 기록 누락은 미완료로 명시한다. D09 69동 전체 통과나 게임 밸런스 변경 승인으로 확대하지 않는다.
