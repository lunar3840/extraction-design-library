# 이미지 기반 미니맵 staging 구현 독립 정적 리뷰

검토 대상: `work/image-based-minimap/Runtime/{TacticalMapData,TacticalMapImage,TacticalMapView}.cs`와 `Editor/{TacticalMapImageBaker,TacticalMapImageEvidence,TacticalMapImageChecks}.cs`. 2026-10-22 staging 상태를 읽기 전용으로 확인했다. Unity 실행·컴파일·스크린샷 대조는 이 리뷰에서 하지 않았으며, 현재 게임 파일이나 Unity `Library`에는 쓰지 않았다. 델타포스는 이미지 표현 참고 범위이며 게임 규칙 검토 대상이 아니다.

## 수정 권고: 지하 플레이어 상태에서 베이크되는 홀 표면 메시

`TacticalMapImageBaker.Bake`는 가림 처리로 꺼진 지붕·외벽 렌더러를 일시적으로 켜고, `finally`에서 renderer 상태·런타임 재질 속성·fog·홀 veil·임시 카메라를 복구한다. 그러나 `StageAHallV13LayerVisibility.UpdateVisibility`는 플레이어가 B1에 있을 때 `SurfaceFilters[i].sharedMesh`를 `UndergroundViewMeshes[i]`로 교체한다. 베이커는 이 `MeshFilter.sharedMesh`를 외부 지형용 `SurfaceMeshes[i]`로 전환하지 않는다. 따라서 지하 상태에서 BakeCurrentStage나 evidence `bake`를 실행하면 동일한 맵인데도 홀 표면이 지하 표시용 메시로 이미지에 굳을 수 있다.

베이크 시작 전 `SurfaceFilters`의 각 현재 `sharedMesh`를 저장하고, 캡처 동안 대응 `SurfaceMeshes`를 적용하며, `finally`에서 원래 메시를 복원하는 편이 안정적이다. 가능하면 지상/지하 두 위치에서 각각 임시 베이크하여 동일한 이미지인지 검사한다. 메인 에이전트에 이 발견을 별도로 전달했다. 근거: `TacticalMapImageBaker.cs`의 renderer 상태 저장·복구 구간(약 103~115, 154~166, 233~250행), 실제 프로젝트 `StageAHallV13LayerVisibility.cs` 82~100행.

## 맞게 연결된 부분

- `TacticalMapView.PlayerMarkerMatrix(parent,pin,heading)`은 `parent * TRS(pin,rotation,1)`이다. `UiTheme.Begin`에서 설정하는 HUD 배율 행렬을 부모로 유지한 채 피벗과 회전을 합성하고, 표식을 원점 중심 사각형에 그린다. 표식의 로컬 원점은 계산상 배율과 방향에 관계없이 그룹 안의 `pin`에 남는다. `try/finally`에서 `GUI.color`와 `GUI.matrix`도 원복한다. 다만 `GUI.BeginGroup`의 실제 클리핑·좌표 원점까지 포함한 픽셀 결과는 정적 산술만으로 확정할 수 없으므로 배율별 게임 화면을 확인해야 한다.
- 베이크 카메라는 맵 루트 로컬 `-Y`를 향하고 화면 위는 로컬 `+Z`다. 직교 크기 `map.height/2`와 `width:height` 비율을 함께 사용하므로 맵 `(0,0)`이 PNG 왼쪽 위, `(520,400)`이 오른쪽 아래가 되는 계산이다. `SampleImage`은 `py=(yMax-mapY)/mapHeight*textureHeight-.5`로 Unity 텍스처의 아래 기준 행을 선택한다. `CopyCircularRegion`은 출력 버퍼의 낮은 Y(아래)에서 맵의 큰 Y(남쪽)를 샘플링한다. 북쪽 고정 방향이 일관된다.
- `Data.Dispose`는 `ownsBackground`가 참인 자체 생성 1×1 대체 텍스처만 파괴한다. `Resources.Load`로 공유된 PNG를 파괴하지 않으며 CPU 픽셀 배열을 놓는다.
- `LoadImage`마다 `ImageRevision`이 증가하고 `DrawRoundPlan`은 데이터 객체·revision·중심 중 하나가 바뀐 Repaint에 원형 텍스처를 다시 만든다. 동일 데이터 객체의 `Rebuild` 이후 원형 지도 캐시도 무효화된다. 이동 중 100ms 지연이 없어 플레이어 표식과 배경이 같은 현재 중심을 쓴다.
- PNG와 JSON이 같은 경로 줄기를 공유하더라도 `Resources.Load<Texture2D>`와 `Resources.Load<TextAsset>`은 타입을 지정하므로 의도한 자산을 구분할 수 있다. [Unity 6 Resources.Load 문서](https://docs.unity3d.com/ja/6000.0/ScriptReference/Resources.Load.html)는 같은 이름의 다른 타입에서 타입을 명시하는 방식을 설명한다. 베이커의 `Projection` JSON에는 런타임이 읽는 schema/west/north/width/height/pixelWidth/pixelHeight가 포함된다.
- 이미지 또는 calibration이 없거나 크기가 맞지 않으면 `UsesImage=false`인 1×1 어두운 대체 이미지를 명시적으로 만든다. 오래된 충돌체 도형 지도로 조용히 돌아가지 않는다. 미니맵은 “지도 이미지 없음”을 표시한다.
- 베이커는 활성 맵 루트 아래의 현재 유효한 `MeshRenderer`를 선별한다. 비활성 GameObject·비활성/강제 숨김 renderer는 배제하고, 등록된 지붕·파사드 가림 대상만 예외로 복구한다. `_Encounter_Raid`, `_Loot_Raid`, Debug/Gizmo/Marker/Spawn/Trigger/Volume 계열을 제외한다. 렌더러·런타임 재질·fog·전역 홀 veil·RenderTexture와 카메라 정리는 예외 시에도 `finally`에서 시도한다. 등록된 roof 분기 전체가 예외 대상이므로 실제 PNG에서 의도치 않은 이전 외장재가 겹치는지는 확인해야 한다.

## 남은 검증·안전 간극

1. `LoadImage`의 `JsonUtility.FromJson`은 예외를 잡지 않는다. calibration 파일이 손상되어 JSON 구문 분석이 실패하면 명시적인 1×1 대체 이미지로 넘어가지 못하고 `Rebuild`가 예외로 중단될 수 있다. 파싱 예외를 잡아 같은 missing-image 경로로 보내는 것이 현재 fallback 의도와 맞다. 런타임은 이미지·JSON의 픽셀 치수 및 A맵 미터 범위를 확인하지만, 픽셀 가로세로가 미터 범위와 같은 축척인지와 실제 이미지 내용이 해당 베이크의 것인지는 검사하지 않는다. 정상 베이커 산출물은 동일 축척이다.
2. `TacticalMapImageChecks.RunLive`는 StageA에 한정된다. evidence에는 StageB 출격·베이크가 있지만 B 이미지는 같은 좌표·픽셀·원형 샘플 검사를 통과하지 않는다. B맵까지 이미지 교체 대상이라면 최소한 B용 로드/종횡비/원형 방향/현재 플레이어 위치 검사가 필요하다.
3. 현재 `PlayerMarkerMatrix` 검사는 행렬 대수로 피벗을 확인하며 실제 Unity IMGUI `BeginGroup` 안의 픽셀 위치를 검증하지 않는다. B1~B4 등 재현 가능한 위치에서 미니맵과 전체 지도를 배율 0.5, 1, 1.2, 1.5 및 방향 0/45/90/180/270도로 촬영해 핀 중심의 스크린 좌표를 이미지와 비교해야 한다. 원형 샘플 검사는 색상 방향을 확인하지만 도로·다리·건물 같은 실물 랜드마크와 표식의 삼자 정합은 화면 검증이 필요하다.
4. 원형 지도는 플레이어 중심이 조금이라도 바뀔 때 256×256 픽셀을 매 Repaint에서 다시 bilinear 샘플링한다. 이는 60fps 기준 약 393만 샘플/초이며, 성능은 아직 실측되지 않았다. 정확한 위치 갱신은 유지하되 실제 플레이 중 프레임 비용을 확인해야 한다.
5. `TacticalMapImageBaker.BakeCurrentStage` 메뉴 항목은 임시 프로필 소유 검사를 하지 않는다. `TacticalMapImageEvidence`의 명령은 `UiKitEvidence/input-`와 interactive ownership을 확인하지만, 메뉴는 일반 Play의 Stage에서도 Resources PNG/JSON을 덮어쓸 수 있다. 팀의 증빙 작업에서는 evidence 경로만 사용하고, 메뉴에도 동일한 제한이 필요한지 결정해야 한다.

`TacticalMapImageChecks.cs`를 이번 정적 리뷰에서 수정하지 않았다. 실제 Unity에서 이미지 검사 실행 결과를 읽고 위 문제 해결 여부와 런타임 픽셀 정합을 재검토해야 완료로 판단할 수 있다.
