## 실제 삼각형 판정과 좌표

`TryIntersectCachedMesh(:588)`는 mesh별 vertices/submesh triangles를 보존하고 submesh tree를 첫 사용 때만 만든다. BVH가 반환하는 hit는 leaf의 **같은 `TryIntersectScaledTriangle` 성공**뿐이다. enclosing AABB를 최종 hit로 삼거나 문/창 구멍을 면으로 메우는 fallback은 없다. 읽기 불가능하거나 mesh가 없으면 false다.

worldRay는 `renderer.worldToLocalMatrix`로 origin/vector를 변환하며 local direction을 정규화하지 않는다. 그러므로 `originLocal+t*directionLocal = inverse(originWorld+t*directionWorld)` 관계를 유지해 단위 world direction 기준 t가 world metre로 남는다. 비균일/음수 scale·회전에서도 같은 t이며, callers가 정규화한 world ray를 넣는 기존 계약을 유지한다. kernel의 `.001 < t < maxDistance`, winding/barycentric/relative determinant 정책도 변경하지 않았다.

BVH node는 실제 소속 triangle 최소/최대로 만들고 mesh span×2e-6 padding을 더한다. slab는 double이고 direction==0인 축은 slab 내부 여부만 확인한다. tree split은 centroid의 최대 분산 축에서 count를 반으로 나누므로 같은 centroid에서도 균형이 유지된다. leaf8에서 반드시 실제 triangle 검사를 거친다. nearest는 현재 best로 뒤 node를 가지치기하고 any-hit는 첫 실제 hit에서 끝낸다. near/far child stack64는 int배열에 담을 수 있는 triangle 개수의 median-balanced tree 깊이보다 넉넉하다. Unity main thread의 동기 query 전제라 한 tree의 reusable stack/entries는 중첩 query나 병렬 query용 구조는 아니다. 현재 leaf 검사에서 그런 callback/재진입은 없다.

## 재질/소유 범위와 해제

일반 reveal은 `eligibleOnly=true`이고 active surface일 때 clone 대신 저장한 Original 재질을 검사한다. nontriangle submesh는 비어 있고 transparent/alpha-cutout 등의 기존 제외 정책은 동일하다. material 부족 시 마지막 slot을 재사용하는 기존 정책도 유지한다.

West historical geometry query는 기존처럼 `eligibleOnly=false`, `nearest=true`로 사용한다. 현재 map에 Reveal component가 있을 때 같은 cache를 재사용하고, component가 없는 legacy 환경에서만 이전 exact linear 경로를 유지한다. legacy가 BVH를 못 찾았다는 이유로 AABB-hit로 바뀌지 않는다.

static batch에서는 `subMeshStartIndex`에서 원래 material개수만큼 owned range를 쓰므로 combined mesh의 다른 renderer 면을 자기 면으로 처리하지 않게 한다. 이는 단순 선형→BVH 외에 범위 보호를 명시한 부분이다. 논리상 타당하지만 아래 실제69검사는 전부 static_batch=False였으므로 실제 static batch 회귀까지 실증됐다고 표현하지 않는다. 현 맵 raw source 범위에는 해당 테스트 공백이 적용되지 않는다.

tree/vertices/index/node/scratch는 map component의 `meshData` 아래 managed 참조다. `ReleaseAll(:906)`의 `meshData.Clear()`로 함께 놓고 별도 static BVH cache·새 native/RT resource를 만들지 않는다. OnDisable/OnDestroy가 기존 재질·overlay·mask와 함께 ReleaseAll을 호출한다. 원본 shared mesh·material 에셋을 파괴하거나 수정하지 않는다. lifetime 중 sharedMesh 내용이 자체 수정되는 동적 architecture mesh에 자동 invalidation을 추가한 것은 아니며 현재 고정 imported 건물 범위와 구분한다.

## 성능은 아직 별도 판정

이 검토 중 읽은 `visibility/runtime_proof_639288581773045026/RUNTIME_PROOF.txt`는 function14PASS/0FAIL이며 실제 RG coverage/rectangle 안 포함·resize/restore, 건물 material원본 reference mismatches0, actor/skinned source mismatches0, 원본material848파일 해시 changed0, disabled runtime veil0을 기록한다. 해제/기능 근거로 수용하되14PASS를 성능 PASS로 바꾸지 않는다.

같은 원문의45sample Editor fullframe 중앙값은 originalCPU53.2443ms→maskCPU144.1204ms, GPU3.9107→5.0196ms다. 이 수치만으로 CPU 문제가 해소됐다고 판단할 수 없다. 메인이 I/O 제외 별도 warm 계측을 진행 중이라고 알려왔다. 최신 원문이 나오면 정확한 source·timing범위·캡처/readback 제외·기본 AI/카메라 조건과 함께 다시 판정해야 한다. BVH의 연산 수 감소는 성능 개선의 구조적 근거지만 전체 Editor frame의 병목이 전부 tree traversal이라는 증거는 아니다.

CPU 후보에 남은 비용은 mesh query당 Transform/material배열 접근·여러 renderer/7sample 순회·원래 architecture 선택과 GPU mask다. 한 번 tree 생성/정렬의 cold 비용과 warm query 비용도 구분해야 한다. root의 추가 계측 결과 없이 임의 FPS 목표·완료 선언을 추가하지 않는다.

임시 helper의 Finish는 wrapper를 event에서 빼고 original delegate를 복구한 뒤 Play를 끝내며 runInBackground와 참조/측정목록을 정리한다. Play 종료의 component OnDisable이 원래 callback·map cache를 해제하는 경로와 맞는다. 공유 Editor를 이 담당이 조작하지는 않았다. 최종 cleanup의 실제 Edit 상태·임시 파일 삭제는 메인 확인 근거와 연결해야 한다.

현재 결론은 **정확성/현 scope 통합 수용, 따뜻한 고정 W03에서 실제 핵심 CPU 메서드 비용을 분리해 확인, 전체 빌드 성능 PASS 주장은 하지 않음**이다. frozen AI의 계측을 실제 삼자전 프레임 부하로 확장하지 않는다.

수치 표는 원문 도구의 Stats 정의를 유지했다. 짝수 n30의 median은 정렬 배열 index15의 upper central sample이고 두 중앙값의 평균은 아니다. 이 표기 차이로 원문 수치를 새 통계치로 바꾸지 않았다. 최종 iteration06 대표6 실제 화면의 후속 판정과4소스/전후18쌍 서명은 `VISIBILITY_PEER_REVIEW.md` 마지막 절 및 `FINAL_VISUAL_SOURCE_SIGNATURES.json`에 연결했다.
