# 독립 게임플레이·아트 소스 검토

2026-10-21. 검토 담당은 실제 프로젝트/에셋을 수정하거나 Unity를 실행하지 않았다. 게임플레이 스테이징, 아트 스테이징 및 통합 중인 실제 UI 소스를 읽었다. 본 보고서와 기존 배치 조사 문서의 요구 범위 오해만 수정했다.

## 현재 판정

**최종 검토 통과. 남은 차단 결함 없음.** 발견한 UI 가방 연결 결함은 메인이 수정했고 실제 수정 소스와 strict N3/정상 사망 정리 N2 Play의 객체 동일성·소비·디스크 재로드 검사로 해결을 확인했다. 확률·프로필·실제 배치·관련 기존 전리품 회귀 및 최종 UI/상세 이미지를 직접 읽었다. 개별 검증의 범위와 한계는 아래 및 VISUAL_REVIEW.md에 기록한다.

### [해결됨, 최초 P1] 복원 성공 뒤 Session.Bag 재연결

- 위치: `C:/UnityProject/escape/Assets/Escape/Runtime/Stage/SessionChipRecoveryView.cs:15` (최초 검토 시점).
- `RestoreRecoveredChip()`은 `Session.RestoreCompanionCargoChip()` 뒤 `Inventory.Refresh()`만 실행한다.
- 복원은 `ProfileChipRecovery.cs:29`의 `Persist(candidate,true)`로 확정되며, 기존 `ProfileSession.Persist()`는 새 가방/창고 객체를 구성해 `Session.Bag`와 `Session.Storage`를 교체한다.
- `InventoryController.Refresh()`는 이미 보유한 `InventoryController.Bag`를 읽어 하중/무기/UI 상태를 갱신할 뿐 새 `Session.Bag`에 연결하지 않는다. 일반 거점 변경의 `CampMutation()` 및 창고 이동의 `Transfer()`가 다시 Initialize/BindPlayer를 호출하는 이유다.
- 가방에서 조각을 소비하는 복원을 하면 저장된 가방은 조각이 줄지만 화면과 실제 조작은 옛 가방을 참조한다. 가방 대체 출력 경로도 새 칩을 즉시 표시하지 못하며, 이후 조작이 세션 가방과 어긋날 수 있다.
- 수정 방향: 기존 `CampMutation()` 또는 동일한 vitals 동기화·Inventory.Initialize/BindGrowthAndItems 경로를 사용한다. 별도 성공 문구는 유지할 수 있다.
- 확인: 실제 `world.RestoreRecoveredChip()` 성공 뒤 `ReferenceEquals(world.Inventory.Bag,world.Session.Bag)` 및 소비된 조각/완성 칩 수, 실패 시 객체/수량 보존을 검사한다. ProfileSession 단독 테스트로는 이 UI 연결 결함을 검출하지 못한다.

재검토: 실제 파일은 이제 `CampMutation(()=>restored=Session.RestoreCompanionCargoChip(character))`를 사용한다. 기존 CampMutation은 성공 뒤 BindPlayer를 호출하고, BindPlayer는 Inventory.Initialize(player,Session.Bag,...)와 BindGrowthAndItems를 수행한다. Refresh만 호출하던 경로가 제거되어 소스 결함은 해결됐다. 후속 strict N3 실제 UI 동작에서 ReferenceEquals, 조각 소비 수량·가방 격자·개체 ID 및 LocalProfileStore 재로드 일치가 모두 PASS임을 읽었다.

## 독립적으로 실행한 확률 검증

기존 스테이징의 `ChipRewards.dll`에 포함된 `StageAChipRewardProbabilityChecks.RunRules()`를 PowerShell에서 직접 호출해 재실행했다. 프로그램의 파일 저장 진입점은 사용하지 않았으며 에셋·사용자 저장 파일을 생성/수정하지 않았다. 이 DLL은 해당 스테이징의 실제 LootCatalog/StageALootRewards 소스와 경계 타입을 컴파일한 결과다. DLL 생성 시각은 보상 소스의 마지막 수정 뒤다. 이 실행은 Unity 프로필 트랜잭션이나 실제 아트를 실행한 것으로 간주하지 않는다.

동료별 20,000시드에서 일반 용기/금고/보스의 완전 칩 관측값은 다음과 같았다.

| 동료 | 일반 용기 | 금고 | 보스 완전 칩 |
|---|---:|---:|---:|
| Edel | 205 (1.025%) | 596 (2.980%) | 1,598 (7.990%) |
| Liv | 209 (1.045%) | 610 (3.050%) | 1,615 (8.075%) |
| Uui | 202 (1.010%) | 592 (2.960%) | 1,597 (7.985%) |

같은 valuables/2단계 기초 풀 비교에서 지정 고가품을 1개 이상 포함한 결과는 일반 10,949/20,000(54.745%), 금고 14,133/20,000(70.665%)였다. 금고 5,867개(29.335%)에는 지정 고가품이 없었다. 35%는 추가 프리미엄 롤 자체의 확률이며 최종 고가품 포함률과 다르다. 완전 칩도 실패 시드가 존재한다. 결정성, 기존 보급품 앞부분 불변, 중복 행 방지, 잘못된 동료 칩 없음, Serin 제외, 비매핑 생활권 칩 제외 검사가 통과했다. 6개 화물 ItemDefinition.Validate()도 독립 호출해 모두 통과했다.

배치 조사 문서에서 HALL 금고를 다른 금고보다 반드시 더 높게 만들라는 조건은 제거했다. 이는 검토자의 과한 제안이었으며 사용자 필수 요구가 아니다. 통과 조건은 HALL 핵심 금고를 포함한 **금고 유형이 일반 파밍 용기보다 고가품 확률이 높고 보장은 아니라는 것**이다. 같은 금고 사이의 별도 서열은 요구하지 않는다.

## 소스에서 확인한 규칙과 경계

- Edel 구역은 HALL/PARTS/N11/E06, Liv는 POWER/N08/N12/N14/E01/E03, Uui는 CLINIC/N03/N05다. 정확히 세 종류만 탐사 화물에 등록되며 Serin은 ID 생성부터 거부한다. 비매핑 구역에는 칩을 추가하지 않는다. 이 시설/동료 연결은 첫 튜닝이며 캐릭터 설정의 사실로 주장하지 않는다.
- 선정된 칩 보스는 N2→Edel, N3→Liv, N4→Uui다. N1/N5/알 수 없는 이름은 보너스가 없다. 후보 선정 자체나 고정 홈은 변경하지 않는다.
- LootTestWorld.OnDefeated()의 실제 적 사망 콜백에서만 보너스를 더한다. 기존 defeatedSources HashSet이 같은 개체의 재통지를 거절하므로 확정 조각이 중복되지 않는다. `Target`은 주입된 플레이어 소유 세션 참조이고, 인간/기계 교전의 `CurrentCombatTarget`과 별도임을 확인했다. NPC에게 처치됐다는 이유로 새 칩 보상을 배제하는 새 코드는 없다.
- 보스의 ‘확정’은 실제 출격에 등장한 해당 개체의 처치 전리품에 조각 1개가 들어간다는 뜻이다. 결장한 후보에게 조각을 선지급하지 않는다. 기존 물리 전리품 위치 찾기 실패 시 드롭이 생성되지 않는 경계는 유지되므로 실제 출격 드롭 배치 검증까지 필요하다.
- 용기 보상은 출격 루트 생성 시 기존 StableSeed(raidSeed,id)로 단 한 번 정해진다. 열기/다시 보기에서 다시 계산하지 않는다. 기존 출격 루트 중복 거절·Clear 경계를 유지한다. 세션마다 BeginRaid가 적 소모 ID를 초기화한다.
- 복원 재료는 같은 캐릭터의 보호되지 않은 조각 5개다. 가방/창고 수량을 후보 복사본에서 확인하고 창고부터 소비한다. 다른 캐릭터 조각으로 대체할 경로가 없다.
- 출력은 후보 창고를 먼저 사용하고 가방을 차선으로 사용한다. 출력 수량이 1개라 부분 성공이 없고, 두 목적지 모두 공간이 없으면 저장·채택 전에 종료하므로 실제 조각은 남는다. 보호 조각은 소비하지 않는다.
- Persist는 프로필 검증과 새 인벤토리 구성을 저장 전에 수행하고 저장 성공 뒤 한 번 채택한다. 저장 실패 시 기존 라이브 객체를 보존한다. Notify는 성공 뒤 한 번이다. 복원은 거점에서만 가능하다.
- 무게 제한을 강제로 새로 도입하지 않고 기존 InventoryState.Add의 과중량 허용 규칙을 따른다. 완전 칩/조각에 양수 무게와 정상 격자 크기가 있으며 판매 불가다. 사망·탈출은 별도 예외 없이 일반 화물의 기존 세션 흐름을 따른다.

## 후속 실제 통합 검증: strict N3

`strict_n3_lifecycle/` 및 당시 루트 `ACTUAL_CHIP_LIFECYCLE.txt`를 읽었다. 실제 선정 N3에 대해 통제 시드 491로 금고와 보스 양쪽을 LootInteractor.Open의 거리·시야·바라보기 조건으로 열었고 대체 LootState 경로를 허용하지 않았다. 실제 DamageReceiver 처치·단일 전리품·같은 피해 재통지/새 치명 요청의 중복 거절, 대응 Liv 조각/완전 칩 재고·수색·가방 이전, 지상 복원 거절, 정상 탈출 저장, 거점 복원, 객체 재연결, 디스크 재로드 일치가 통과했다. 처음 N4 대체 경로 결과는 diagnostic_initial_lifecycle로 구분되며 실제 수색 UI 완료를 증명하는 로그로 사용하지 않는다.

초기 N4의 시체 가림 의심은 검증에서 모든 적을 Frozen=true/UseAutomaticTicks=false로 묶은 데 따른 조건이었다. EnemyController.Update를 읽어 해당 플래그가 사망 후 2초 충돌 비활성/3.6초 제거보다 먼저 반환함을 확인했다. 실제 런타임의 시야 판정을 느슨하게 바꾸지 않고 정상 사망 정리 경로를 허용한 검증으로 재시도하는 것이 맞다.

실제 최신 UI 소스도 읽었다. SessionChipRecoveryView는 CampMutation 성공 후 `Chip restored: <이름>` 상태 키를 만들고 UiTheme.cs의 UiText.SessionStatus는 이를 한국어 성공 문구로 표시한다. GlassIcons.DrawUpright는 generic item fallback보다 먼저 CompanionChipCargoCatalog.IsCargo를 처리하며, 완전 칩은 사방 접점이 있는 정사각 칩, 조각은 깨진 기판 형태를 DrawRecoveredChip으로 그린다. 이는 새 화물의 식별 표식 지원이며 다른 모든 아이템이 새 3D 모델로 바뀌었다고 주장하지 않는다.

## 최종 정상 사망 정리 검증과 보존 확인

`strict_n4_lifecycle/`라는 디렉터리에 저장됐지만 실제 선정 보스가 N2였음을 로그 첫 부분에서 확인했다. N4가 출격에 없어서 기존 선정 명단의 다른 해당 보스를 선택한 것으로, N4 실제 UI 통과 기록으로 취급하지 않는다. 이 실행은 시드 1849의 **N2 정상 사망 정리 검증**이다.

전체 로그와 PNG 3장을 읽었다. 실제 DamageReceiver 처치 뒤 source의 Frozen/자동 틱 검증 조건을 정상 사망 처리에 맞춰 풀고 실제 게임 시간 2.2초를 기다렸으며, 기존 Enemy.Update가 시체 콜라이더를 끄거나 제거했음을 검사했다. 이후 같은 거리·바라보기·시야 조건의 실제 LootInteractor로 보스 전리품을 열었고 직접 상태 대체는 허용되지 않았다. 일치하는 Edel 조각/완전 칩, 단일 드롭/재치명 중복 거절, 검색→가방→탈출→5조각 복원→라이브 가방 소유권→실제 LocalProfileStore 재로드가 모두 통과했다. 화면은 Edel 완전 칩 3개와 성공 문구를 올바르게 표시한다.

처음 대체 경로를 사용한 N4 사례를 생산 코드의 영구 상호작용 결함으로 단정하지 않는다. 기존 상호작용 시야 규칙을 완화하지 않고 검증 fixture의 사망 정리 조건을 바로잡았으며, 실제 N3/N2 경로가 통과했다. N4는 규칙·프로필·정적 배치 검사와 초기 사망/드롭 데이터 검사가 있으며, strict 실제 수색 UI를 N4에서도 직접 완료했다고 확대하지 않는다.

실제 A 씬과 Resources 맵 프리팹을 검토 시점에 다시 SHA256 계산하여 BASELINE_MAP_HASHES.txt와 정확히 같은 값임을 확인했다. 씬은 `C9E3D324A6DA7849188D1D92F9D79843B8E4820DCBE8325C3A0B227CD13D1874`, 맵 프리팹은 `4DB8ACD70D7603528305FC410031104E9388BDB571A313D9965FB17895317FC4`다. 기존 clean companion 선택/목록 3개 파일도 보존 명세의 Before와 실제 재계산 해시가 일치한다.

최종 승인 범위는 실제 50개 유한 용기, 금고의 상대 확률 상향/비보장, 세 종류의 구역별 화물·세 보스 대응 보너스, 보호 재료/원자 저장을 적용한 거점 5조각 복원, 저장/탈출/사망의 일반 화물 의미와 해당 UI다. 정화·Liv/Uui 모델/동료 해금·장기 파밍 속도·모든 무작위 출격의 경제 및 전투 밸런스는 완료한 것으로 주장하지 않는다. 이 추가 기능을 이번 완료 조건으로 새로 요구하지도 않는다.
