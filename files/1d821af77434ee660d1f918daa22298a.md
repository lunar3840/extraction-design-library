# 체스트리그·배낭 분리, V 자동 치료 및 정보창 가독성

작업일: 2026-10-23 (Asia/Seoul). Figma·Unity 반영 및 이번 범위의 통합 검증 완료.

## 사용자 지시와 의도

- 기존 3·4·5 퀵슬롯을 없애고 V 입력당 상태에 맞는 회복 아이템 하나를 자동 사용한다. 사용자 답변으로 자동 선택 방식이 확정되었다.
- 체스트리그는 장착 아이템이 아닌 항상 주어지는 기본 파밍·준비 공간이다. 배낭에만 있는 소모품은 V 대상에서 제외하고 인벤토리에서 직접 사용한다.
- 배낭 아이템을 추가한다. 중앙 패널은 리그 위, 배낭 아래이며 최대 크기에서도 아이콘과 글자가 읽혀야 한다.
- 진통제는 무부상 상태에서도 미리 사용할 수 있다. 자동 V는 치료가 필요한 상태에서만 선택한다.
- 최상위 마우스 정보창은 불투명도를 크게 높여 아래 슬롯과 글자가 비치는 문제를 해결한다.

## 첫 적용 수치와 참고 범위

기본 리그6×2=12칸, 배낭6×3/6×4/6×6=18/24/36칸, 최대 소지48칸으로 잡았다. 이는 이번 UI와 기본 밸런스를 위한 첫 적용값이다. 아이템 형태는 리그의 독특한 모양을 복제하지 않고 일반 격자로 표현한다. 공식 자료로 확인한 ‘리그 준비 보급/배낭 전리품 운반’ 원리를 참고했고, 다른 게임의 장착형 리그·빠른 사용 예외·칸 수는 우리 게임 확정 규칙으로 옮기지 않았다. 출처와 불확실성은 reference-research.md에 있다.

## 변경 전 증빙

before_inventory.png와 상태 텍스트는 실제 코드 수정 전 SystemsTest 격리 프로필에서 새로 캡처했다. before_figma.png는 편집 전 공식 MCP 스크린샷이다. source_before/Runtime에 원본 코드를 보존했다. before_hover.png는 바로 앞 작업의 실제 hover 캡처를 복사했다(정보창의 해당 코드·명암은 이번 변경 전까지 동일). before_editor.png는 앞 작업 종료 시 복구된 원래 StageA 편집 화면의 실제 캡처를 복사했다. 모두 합성·재구성 이미지가 아니다.

## 구현 방식

- 소지품 소유자인 Bag은 한 개로 유지하고 내부 페이지0을 리그,1을 장착 배낭 공간으로 구별한다. 무기·의료품·칩의 인스턴스 참조를 불필요하게 교체하지 않는다.
- 구획별 경계, 다중 칸·회전·교환과 정렬을 적용했다. 자동 정렬로 배낭 의료품이 리그에 올라오지 않는다.
- 배낭의 무게·장착·교체·해제·창고 보관·빈 배낭 드롭·수색 후 직접 장착을 연결했다. 작은 배낭에 내용물이 안 맞거나 교환 공간이 없으면 전체 작업을 거부한다. 채워진 배낭은 먼저 비워야 해제·드롭할 수 있다.
- 거점 배치·분할과 배낭 변경은 저장 트랜잭션을 경유한다. 실패하면 UID·수량·좌표·장비 상태를 복원한다.3×3 대형 배낭은6×2 리그에 들어가지 않으므로 창고로 직접 해제하는 별도 경로도 제공한다.
- 구버전 프로필은 기존6×6 배치를 우선 배낭에 보존하고, 초과분은 리그 및 복구 보관함에 보존한다. 대형 배낭 지급은 이전 버전 필드로 한 번만 수행한다. 기존 성장 값은 무게 훈련으로 유지한다.
- 사망 시 기본 공간은 남고 장착 배낭은 일반 장비처럼 손실·회수 규칙에 포함한다. 깨끗한 동료 칩과 최신 출격 중 테스트 장착 지시는 보존한다.
- 새 게임의 기존 시작 장비를 삭제하지 않도록 리그12+표준 배낭24=기존 총36칸을 유지하고, 큰 방탄복·헬멧을 작은 보급품보다 먼저 배치한다. 실제 추가 순서와3개 칩의 UID 보존까지 별도 회귀 검사한다.
- V는 리그 안에서 정확한 UID 하나만 선택하여 시작한다. 자동 연속 사용·의료휠·3·4·5 입력은 제거한다. 배낭 직접 사용, 메뉴·지도·사망·입력 잠금을 유지한다.
- 마지막 사용 횟수 소비가 Bag.Changed를 발생시키는 동안 사용 취소가 재진입하여 수술·진통 효과를 지우지 않도록 Tick 가드를 추가했다. 실제 리그 밖 이동에 따른 취소는 유지한다.
- Figma 원본105:2987을 기존 컴포넌트·토큰·Noto 서체로 수정했다. 원본의 변경 전 복제본139:584와 배낭 미장착144:799도 남겼다. 좌측 캐릭터 크기와 배경판 제거는 유지한다.
- 공통 간격90px, 한 칸의 실제 카드82px, 간격8px로 최대8행이 기존 중앙 패널에 들어가도록 했다. 퀵슬롯 영역은 없앴다.
- 정보창 바탕98% + 티어 색층24%로 합성 불투명도98.48%를 적용했다. Figma의6개 티어와 Unity 렌더러가 같은 기준이다. 슬롯 본체의 기존 반투명 표현은 유지한다.
- Figma HUD103:2538의 기존 퀵슬롯 그룹을 숨기고 V 자동 치료 안내 한 개로 교체했다. before_figma_hud.png와 after_figma_hud.png는 공식 캡처다. 이번 런타임 HUD 수정 전 단독 게임 화면은 별도로 저장하지 못했으며, 인벤토리 before 캡처와 원본 코드·Figma 전 이미지는 보존되어 있다. 사후 HUD 이미지를 전 이미지로 사용하지 않는다.

## 검증

전체 Runtime/Editor 컴파일 오류0개, 기존 경고 각각21/35개. 독립 실제 도메인17/17검사와 시작 장비 재현검사를 통과했다. Unity Edit에서 ChestRigBackpackChecks(55), AnalgesicProphylaxisChecks(42), RigQuickUseChecks(56), InventoryRegionSwapChecks(60), GroundLootChecks(65), LootEquipmentChecks(81), 총359개 확인 항목을 모두 통과했다. 새 게임 시작 장비·프로필 검증도 포함한다. 2,000회 무작위 기하 oracle 검사를 포함한 기존 지역 교환 검증의 의미도 유지한다.

초기 검증 중 발견한 문제도 보존한다. checks-summary_initial.txt에는 구형 Profile fixture를 새 carried 구조로 바꾸기 전의 실패가 남아 있다. 기하·저장실패·자원 참조 검증의 의미는 유지하면서 해당 fixture만 고쳐 최종 모음을 통과했다. 첫 Play의 작은 배낭에 기존 장비를 순서대로 넣는 방식은 방탄복이 들어갈 연속 공간을 남기지 못했다. 시작 배낭을 표준형으로 하고 큰 물품부터 배치하는 방식으로 수정했으며, 전체 로그에 해당 초기 실패를 포함한다. 원래 사용자 세이브는 사용하지 않았다.

### 실제 Play 확인

- 실제 1920×1080 GameView에서 새 프로필의 표준24칸, 대형36칸, 미장착0칸과 항상 유지되는 리그12칸을 확인했다. 최대 배낭의 여섯 행까지 중앙 패널 안에 표시되며 왼쪽 캐릭터 영역은 유지된다.
- 마우스를 실제 방탄복 슬롯 위로 이동해 정보창이 다른 슬롯과 겹친 상태를 확인했다. 이전과 같은 티어 색과 동적 정보가 유지되고 아래 아이콘·문구는 비치지 않는다. `after_hover_opaque_final.png`가 최종 캡처다.
- V는 Unity Input System 가상 키보드에 실제 down/up 이벤트를 큐에 넣고 production Update가 받는 방식으로 검증했다. 0.8초 동안 키를 눌렀어도 한 번만 시작됐고 의료휠은 열리지 않았다. 체력75→100, 같은 리그 주사기 UID의 자원30→4.999976(부동소수 오차 포함 약5), 나머지 의료품·UID·횟수는 그대로다. 상세 이벤트는 `SIMULATED_INPUT_v_20261022T195353762.txt`, 별도 상태 비교9항목은 `play-verification.json`에 있다.
- Windows 자동 조작 도구의 V 전달 시도 두 번은 게임 상태 변화를 만들지 못했다. 이를 물리 키보드 성공으로 보고하지 않는다. Unity 입력 이벤트 경로 검증과 OS 입력 검증은 구분한다.
- 진통제는 실제 Play에서 체력100·외상0 상태로 직접 사용 API를 호출하고 자연스러운 사용 완료를 기다렸다. 동일 UID의2회분이1회분이 되고 진통 효과 시간이 남아 있음을 확인했다. 인벤토리 사용 버튼을 OS로 클릭한 검사라고 주장하지 않는다.
- 배낭 변경과 미장착 화면 준비는 격리 프로필에서 공개 인벤토리·세션 API를 사용하는 검사 fixture다. 실제 사용자 프로필이나 사용자 세이브를 변경하지 않았다.

### 검사 중 발견한 도구 오류와 로그 범위

대형 배낭의 첫 화면 준비에서 창고의 기존 탄약20개와 퇴피한 탄약 두 스택이 자동 합쳐졌다. 총량은 보존됐지만 원본 UID별 수량이50/50에서50/20으로 달라졌고, fixture가 과거 수량50을 요구해 복원 루프를 중단했다. `after_large_setup_partial.png`와 `bridge_error_large_fixture.txt`는 이 실패를 그대로 보존한다. 장착 자체는 성공했으며 제품 로직 오류는 아니었다. fixture의 퇴피·복원을 정확한 빈 위치로 옮기는 방식으로 고친 뒤 새 격리 프로필에서 모든 UID·수량 보존과 최종 대형 화면을 다시 확인했다.

요청 파일을 쓰는 순간 Unity가 읽어 발생한 일시적인 Sharing violation도 전체 로그에 남아 있다. 요청은 이후 정상 처리됐으며, Python 요청 유틸리티는 닫힌 임시 파일을 원자적으로 게시하도록 수정하고 최종 status 요청의 정상 처리를 확인했다. `editor-log.txt`와 `log-audit.json`은 최초 Play부터 복구까지 보존하므로 초기 fixture 예외4건과 이 I/O 예외1건이 포함된다. 기존 `Particle Velocity curves must all be in the same mode` 메시지도 남아 있어 전체 Console 무오류를 주장하지 않는다. 컴파일 오류는0개다.

## 주요 파일·최종 상태
